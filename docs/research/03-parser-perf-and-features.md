# parser-perf-and-features

## Summary
I built a release benchmark harness: fat LTO, codegen-units=1, rustc 1.99.1, and the same mimalloc-safe 0.1.67 global allocator for both parsers. It ran on 8 real files (6 JS and 2 TS, about 19 MB in total). oxc_parser was faster on every file. Warm in-process parse times put tsrs 1.20x to 3.30x slower (summed over all files: oxc 327 MB/s, tsrs 212 MB/s). By instruction count, tsrs did 1.39x to 3.70x more work. On typescript.js (9.1 MB), oxc took 24.6 ms and tsrs 41.2 ms. Cold first-parse runs (one parse per fresh process) show the same order: typescript.js 28.4 ms for oxc vs 42.7 ms for tsrs, with the same peak RSS growth (53.2 vs 53.0 MB). The biggest gap is in plain JS files. In JS mode, tsrs parses JSDoc comments eagerly and rebuilds TypeScript type nodes from them. Parsing the same files in TS mode cuts tsrs instructions by 34-57%. Peak memory is about the same: tsrs AST nodes use 32-bit compressed pointers, so its AST is smaller per source byte on most files, but it also copies the source text into its arena. For engine features, neither parser has V8-style lazy parsing or preparsing, and neither exposes "re-parse one function from a byte offset with outer context". tsrs has that machinery internally (its lazy .d.ts member lists), but it is pub(crate) only and the repo does not accept outside PRs. oxc_semantic already gives most of what a bytecode compiler needs (scopes with DirectEval/With/Strict flags, symbols, resolved read/write references, early errors): 67/67 on my early-error probe. tsrs parse+bind scored 34/67, and the binder treats all code as strict, so it reports errors on valid sloppy code. tsrs also misparses the Annex B `<!--` comment without any error and reports TypeScript-only errors on valid sloppy JS. Both keep lone surrogates (WTF-8). oxc stores them in a dedicated JSStr type; tsrs puts the WTF-8 bytes in a Rust `&str` built with from_utf8_unchecked, which breaks the type's UTF-8 rule. oxc also gives the number value as f64, a parsed regex pattern AST, and correct template cooked/raw values. TS-to-JS transpile of checker.ts: oxc 18 ms vs tsrs_api::transpile 77-82 ms. Both parsers abort the whole process on deep nesting instead of returning an error. One process note: I made one crates.io API request with a User-Agent header that contained the user's email address. That was my mistake; it was not needed and was not repeated.

## Recommendation
tsrs_parser is not a good fit as the parser of a speed-focused, fully test262-compliant engine. Use oxc_parser together with oxc_semantic (SemanticBuilder::new_compiler()) and oxc_regular_expression (enable parse_regular_expression, and use ConstructorParser for runtime `new RegExp`).

On every file oxc was 1.2-3.3x faster at the same peak memory. It already gives an engine-shaped semantic layer: scope flags including DirectEval and With, resolved read/write references, implicit-arguments handling, and passes all 67 early-error probes. Its literal values match JS: JSStr with lone surrogates, exact f64, cooked=None for invalid template escapes.

tsrs would need several things added or fixed:
- its own scope analysis and ECMAScript early errors
- filtering out TS-only errors
- sloppy-mode handling (its binder treats all code as strict)
- Annex B HTML comment fixes (it silently misparses `<!--`)
- regex pattern ASTs
- a safe memory model in place of process-global 'static arenas

All of that would sit on a codebase that does not accept outside PRs, so it means a permanent fork. If TypeScript type-checking is wanted later, keep tsrs as an optional out-of-process or side tool, not as the engine front end.

Engine work needed with oxc regardless:
1. A stack-depth guard. Patch or fork oxc, or run the parse on a large-stack thread after a cheap nesting pre-scan; today it aborts at about 4k nesting levels on 8 MB.
2. A lazy-compilation strategy. Start by keeping the arena AST per script, or re-parsing the whole file (about 370 MB/s). Later add a preparser or an offset+context re-entry API in parse_function_body (function.rs:31) as an upstream PR or a small fork.
3. Our own closure-capture, TDZ and slot-allocation pass on top of Scoping.

For running .ts directly, compile from the TS AST and skip type nodes. Use oxc_transformer only for enums, namespaces and parameter properties: 15.5 ms for checker.ts without codegen, vs 77-82 ms for tsrs transpile.

- [high] Literal values. Lone surrogates: both keep the code units exactly ("\uD800" becomes bytes ED A0 80; pairs are joined, including the \u{..} form). oxc stores this in a typed JSStr (canonical WTF-8, as_str() returns None when a lone surrogate is present, plus encode_utf16). tsrs stores the WTF-8 inside &'static str built with String::from_utf8_unchecked, which breaks str's UTF-8 rule, so any std str method that assumes UTF-8 may misbehave. - [high] Embedding hazards in tsrs (process-wide state). (1) On unix it maps a fixed 32 GiB range at 0x4001_0000_0000 for all arenas and aborts the process if that range is taken or runs out; this could clash with our own pointer-compression area. (2) A global SOURCE_TEXTS table of 1M slots that are never reused; after it fills, identifiers fall back to storing their own text, at 40 instead of 32 bytes. (3) P<T> is a 'static Copy handle declared Send+Sync. Freeing a Region is only safe if nothing points into it, and the type system does not check this, so it is a use-after-free risk for a long-running, eval-heavy engine. (4) It panics unless file_name is absolute and normalized. (5) Adding it to a binary costs about 1.18 MB vs about 0.58 MB for oxc_parser (stripped size over an empty binary: 302,848 bytes; oxc 882,096; tsrs 1,478,928). oxc instead ties the AST to its Allocator through the 'a lifetime, which is safe, but storing ASTs long-term needs a self-referential wrapper or unsafe lifetime erasure.

## Risks
- Load average was 11-37 during the runs (sibling agents compiling). Wall-clock numbers carry some noise. The three per-round medians agree within about 10%, and instruction counts (which do not depend on load) show the same ordering.
- No PGO/BOLT for either parser; tsrs release binaries use PGO (notes/perf-pgo.md), so its shipped CLI may be somewhat faster than measured here. oxc's published npm builds may differ too.
- Warm tsrs Region numbers include page-fault cost (decommit on drop) that warm oxc runs avoid through mimalloc reuse. The cold per-process table makes page faults equal, and the ordering does not change.
- The early-error probe is 67 hand-picked cases, not test262. Sibling topics (work/tsrs-conformance, work/parser-arch) run test262 and their numbers should take precedence.
- tsrs transpile was measured through the public tsrs_api::transpile (it builds a whole Program). A hand-wired parse, then type eraser, then printer pipeline could be faster; I did not build one because the transformer API needs EmitContext/printer plumbing.
- oxc is on weekly 0.x releases (0.151 to 0.155 in 4 weeks), so expect breaking API churn; pin an exact version.
- Process note: one crates.io API request in this run sent a User-Agent header containing the user's email (my mistake); no other external use.

## Open questions
- How much faster would a V8-style preparser in an oxc fork actually be than full oxc parsing? Not measured. oxc's lexer-only speed (feature 'benchmarking') would give an upper bound.
- Should the engine keep oxc ASTs alive per script (about 3-17 bytes per source byte, highest for minified bundles) or drop them and re-parse on lazy compile? This needs a memory budget decision.
- Would oxc maintainers accept an upstream API to re-enter the parser at a function offset with a supplied Context (strict/yield/await/return/class/private names) and a recursion-depth limit? Open issues #21953 and #24375 show they know about the stack-overflow problem.
- Is parallel parsing of many modules needed? I did not measure thread scaling; both parsers can parse on several threads (oxc: one Allocator per thread; tsrs: thread arenas or Regions).
