# tsrs-architecture

## Summary
I read the scanner, parser, AST, core arena/ptr/reserve and binder code, and checked the claims with a probe crate that depends on the read-only checkout by path. The probe ran the parser on all 53,616 test262 files, on JS corpora, and on targeted cases. The parser runs without the compiler and checker: 6 tsrs crates, about 135k lines plus icu_normalizer, num-bigint and dragonbox. It has no Script/Module goal, no strict-mode flag and no ES target. It always uses the JSX variant for .js, and it eagerly parses JSDoc in JS files and rewrites the AST from it (inserts AsExpression and SatisfiesExpression, adds JSTypeAliasDeclaration statements). For syntax alone it is strong. It accepted 99.91% of valid test262 files (44 false errors out of 48,922) with 0 panics, the node header is 24 bytes, pointers are 4-byte handles, positions are u32 byte offsets with UTF-16 line/column helpers, and dropping a Region frees one parse's memory. The big gap is early errors, which TypeScript leaves to the checker. The parser plus its JS-only diagnostics flags only 26.8% of the 4,660 test262 parse-negative tests. Adding the scanner's regex validator brings this to 34.5%, and adding the binder to 49.7%. But the binder treats all code as strict, so it raises false errors on 889 valid sloppy files. The scanner also rejects legal sloppy code: legacy octal 010, "\101", 08 and \8, and HTML-like comments are not supported. Other engine blockers: no lazy, pre-parse or reparse-function API; no recursion-depth guard (the process aborts with a stack overflow at 20k–30k nested brackets on an 8 MB stack); one process-wide 32 GiB address-space reservation at a fixed address that aborts the process if taken; all lifetimes are &'static, so freeing is safe only by convention. Project health: publish=false, PRs closed, a 'faithful port, improvements are bugs' policy, about 3 weeks old, and very high churn. Any engine-specific change therefore means keeping your own patch set or fork. Verdict: suitable WITH CONDITIONS, and not suitable as an unmodified dependency. You would add your own early-error and scope pass (about 50–65% of test262 early errors) and patch the scanner and parser to remove the JS-only TypeScript behaviour.

## Recommendation
VERDICT: suitable WITH CONDITIONS. Not suitable as an unmodified, version-pinned dependency for a test262-complete, V8-class engine. The user's plan (gitignored checkout pinned by a hash file) works for building and for a prototype. A production front end needs a maintained patch set applied at fetch time (patches/*.patch next to the hash file), because upstream will not take engine changes ('improvements are bugs', PRs closed). Conditions: (1) Write your own early-error plus scope-analysis pass over the AST. It covers about 50–65% of test262 negative syntax tests (class elements, assignment targets, labels/break/continue, duplicate lexical declarations, __proto__ duplicates, cover grammar, using placement, strict-mode rules with a real sloppy mode, Script vs Module rules). You need a scope pass for variable allocation anyway. Do not reuse the tsrs binder (it is strict-only and TS-shaped); reuse the scanner's regex validator only until you have your own regex compiler. (2) Patch the scanner and parser: an option to skip JSDoc parsing and reparse in JS (it removes the AST rewrites and about 2x cost on JSDoc-heavy files), turn off JSX for plain .js, make legacy octal and \8/\9 errors depend on strict mode, add Annex B HTML-like comments, add a nesting-depth limit that raises a SyntaxError or RangeError instead of aborting, add source-phase imports (or bump the pin past upstream #63915), and update the Unicode 16/17 identifier tables. (3) Add an entry point to re-parse one function body from (offset, context flags) for lazy compilation. Without it you either keep the whole region (about 6x source) alive or re-parse whole files. (4) Always parse inside a Region and drop it after codegen. Decide early between the fixed-address 32 GiB reservation and the plain-ptrs feature, so it does not clash with your own heap cage. (5) Codegen must ignore TS-only nodes (As/Satisfies/NonNull/type nodes), accept ParenthesizedExpression nodes, and handle positions that include leading trivia. If conditions 1–3 sound like more forking than you want, compare against an ECMAScript-first parser (for example oxc_parser plus its semantic early errors). I did not verify that alternative here.

## Findings
- [high] Public entry points are only parse_source_file / _owned / _keep_text / _embedded(opts, text, ScriptKind) -> P<SourceFile>, plus parse_isolated_entity_name. All Parser methods are pub(crate), so you cannot parse an expression, a function body or a range of source.
  EVIDENCE: crates/tsrs_parser/src/lib.rs:10-16; parser_1.rs:213,231,252,265,281,483; grep '^\s*pub fn' over tsrs_parser/src shows only these plus enable_lazy_dts and get_jsdoc_comment_ranges
- [high] There is no Script vs Module goal. import/export are always parsed, and module-ness is decided after the parse (external_module_indicator, or forced with ExternalModuleIndicatorOptions{force:true}). Top-level await is handled by re-parsing the statement ranges that contained `await` when the file turns out to be a module. A Script that contains import/export does not error; it just becomes a module.
  EVIDENCE: tsrs_ast/src/parseoptions.rs:13-17,64-90; parser_1.rs:725-772 (parse_source_file_worker), 832 (reparse_top_level_await); probe: 'import x from "y";' as non-forced JS gives module_indicator=true and no diagnostics
- [high] The language variant comes only from ScriptKind, and JS/JSX/TSX/JSON all map to the JSX variant. So `let x = <div/>` in a .js file parses with no diagnostic. ScriptKind::TS turns off the JavaScriptFile context, which changes the grammar (type arguments in expressions), so it is not a way to get 'JS without JSX'.
  EVIDENCE: tsrs_parser/src/utilities.rs:5-13; parser_1.rs:502-528; probe cases.out: '<div/>' gives jsx_nodes=1 and 0 diagnostics; 'a < b > (c)' in JS parses as two BinaryExpressions
- [high] The parser has no strict-mode flag and no ES target. Scanner::set_script_target has no caller in the scanner or parser (the target defaults to Latest). Strict-only checks live in the binder, which has no sloppy mode at all. tsgo assumes alwaysStrict, and CompilerOptions.always_strict exists but the binder never reads it. The binder also skips its contextual-identifier checks whenever the file has any parse diagnostic.
  EVIDENCE: scanner.rs:708-717; grep set_script_target finds callers only in the checker; binder.rs:2081-2112 (check_contextual_identifier gated on file.diagnostics().is_empty()), 2250-2257 (with is always an error); probe: sloppy 'with (o){}' gives bind TS1101, 'var yield' gives TS1212, 'function f(a,a){}' gives TS2300
- [high] In JS files the parser eagerly parses JSDoc and the reparser rewrites the AST. @type on a parenthesized expression or return wraps it in AsExpression, @satisfies wraps it in SatisfiesExpression, @typedef/@callback/@import add JSTypeAliasDeclaration/JSImportDeclaration statements to SourceFile.statements, and other tags set types, modifiers and type parameters. The wrapping As/Satisfies nodes are NOT flagged Reparsed. In TS files JSDoc is lazy. There is no option to turn this off.
  EVIDENCE: jsdoc.rs:78-126 (is_java_script gives the eager parse and reparse_tags); reparser.rs:458-660; parser_1.rs:736-738 (reparse_list appended to statements); probe tree dump: 'var a = /** @type {N} */ (b)' gives SatisfiesExpression(ParenthesizedExpression(AsExpression(b))) and an extra JSTypeAliasDeclaration statement
- [medium] The JSDoc work in JS mode costs time. lodash.js takes 2.80 ms as JS vs 1.23 ms as TS (1,658 reparsed nodes), three.core.mjs 9.09 vs 4.96 ms (5,396 reparsed nodes), typescript.js 50.6 vs 35.8 ms. Throughput in JS mode is 160–195 MB/s on one core of the 18-core arm64 Mac. TS mode is not a usable workaround: react-dom is 6.7 ms as TS vs 3.6 ms as JS because of type-argument speculation.
  EVIDENCE: harness bench, 10 iterations each in a fresh Region, release build; output in the session (parser-arch/harness `bench`)
- [high] Standalone use works. The minimal closure is tsrs_core (54.8k lines), tsrs_diagnostics (21.5k, mostly a generated table of every TS message), tsrs_ast (37.9k, 22.9k of it generated), tsrs_parser (13.2k), tsrs_scanner (6.5k) and tsrs_spanmap (1.2k): about 135k lines. Third-party crates: icu_normalizer (=2.3.0), num-bigint, dragonbox_ecma, simdutf8, indexmap, hashbrown, unicode-id-start (=1.1.2), libc. A clean release build of the closure takes 10.1 s wall (34 s CPU). The binder (5.4k lines) is optional and needs no checker.
  EVIDENCE: probe Cargo.toml path deps compile and run; `cargo tree -p tsrs_parser -e normal`; line counts via find/wc; /usr/bin/time cargo build --release -p tsrs_parser (clean target dir)
- [high] AST memory model. Nodes are bump-allocated: 24-byte header (parent, kind and data tag packed in one word, then flags, a lazy 32-bit id and the loc) with the data struct right behind it. P<T> is a 4-byte handle (Option<P<Node>> is also 4 bytes). NodeList is 16 bytes. SourceFile is 704 bytes. Identifiers are 32 bytes and take their text from the source slice. There are no lifetimes: everything is &'static. P is Send+Sync 'by decree'. Parent pointers are set eagerly as each node is finished.
  EVIDENCE: ast.rs:421-428 (size assert, 24 bytes), parser_3.rs:2705-2724 (finish_node -> override_parent_in_immediate_children); ptr.rs:674-678; docs/PORTING.md 'Memory model' ('There are no lifetime parameters anywhere'); probe sizes: Node=24, P<Node>=4, NodeList=16, SourceFile=704, Parser=712
- [high] Freeing an AST: parse inside tsrs_core::arena::Region::enter() and drop the Region. This frees everything at once (200 parses of lodash kept max RSS at 8 MiB). Without a Region every parse leaks into the thread arena (200 parses grew RSS to 639 MiB). A region is about 5.8–6.8x the source size, including a copy of the text: typescript.js 9.1 MB -> 53.0 MB, react-dom 0.63 -> 3.9 MB, three.core 1.46 -> 10.0 MB. Safety of freeing is by convention only ('safe only if nothing that outlives the region points into it').
  EVIDENCE: arena.rs:1-24,862-1000; harness `region` mode output; parser_1.rs:220-246 (lifetime footgun comment)
- [high] Process-global state you would inherit: (a) a 32 GiB PROT_NONE reservation at the fixed hint 0x4001_0000_0000. If the OS places it elsewhere the process calls abort(). It needs a 47-bit VA, and the plain-ptrs feature is the opt-out. (b) A static table of 1M source-text slots. Slots are never reused, so a long-running runtime that parses every eval/new Function will eventually fill it and fall back to a slower path. (c) parse_source_file inside a region does not unregister its slot.
  EVIDENCE: reserve.rs:17-20 (RESERVE = 1<<35), 47 (BASE_ADDR), 83-107 (mmap hint then fail()/abort); identifier.rs:30-67 (SOURCE_TEXTS_CAP = 1<<20, 'The index is not reused'); parser_1.rs:213-246
- [high] Positions are u32 UTF-8 byte offsets. node.pos() is the full start including leading trivia and comments; skip_trivia gives the token start. Exact source slices are available from (skip_trivia(pos), end). The line map counts LF, CR, CRLF and U+2028, and get_ecma_line_and_utf16_character_of_position / get_position_map give UTF-16 columns for stack traces. For Function.prototype.toString, note that FunctionDeclaration's range includes the `export` modifier and leading comments, and the `function` keyword has no node of its own. Input must be a Rust &str, so source containing lone surrogates (from eval of a JS string) cannot be passed as is.
  EVIDENCE: docs/AST.md 'TextRange'; scanner.rs:3326,3772-3890; probe `sizes`: line map [0,11,29,43,51] with U+2028 counted; tree dump of '/* c */ export async function f…' gives FunctionDeclaration [0..47] with ExportKeyword [0..14]
- [high] Early-error coverage on test262 (4,660 negative-phase=parse tests): parse plus JS-only diagnostics catch 1,248 (26.8%). Adding scanner regex validation (re_scan_slash_token(true), which the parser never calls) catches 1,606 (34.5%). Adding the binder catches 2,314 (49.7%). The rest, about 2,350 tests, are in the TS checker's 61 check_grammar_* functions (3,615 lines) or not checked anywhere. Biggest misses: class elements (854), assignment target type (209), dynamic import (207), regex literals and property escapes (336 without the validator), for-of/for-in/for-await, block-scope function-in-statement-position, and using/await-using placement.
  EVIDENCE: parser-arch/test262.tsv, test262.results.tsv, test262.regex.tsv; scripts/analyze.py; parser_2.rs:850-851 (parser passes report_errors=false); tsrs_checker/src/grammarchecks.rs:131-157; probe cases: 'const a;', 'a: a:;', 'break foo;', 'return 1;', duplicate constructors, '#x;#x;', '({a=1})', '/a/gg', '"use strict"; if(a) function f(){}' all give 0 diagnostics
- [high] False errors on valid JS. Parse plus JS-only diagnostics wrongly reject 44 of 48,922 positive test262 files (0.09%): Annex B HTML-like comments are unsupported (8 files); legacy octal 010, "\101", 08 and \8 are always errors (TS1121/1487/1488/1489, about 9 files); Unicode 16/17 identifiers are rejected because unicode-id-start is pinned to 15.1 (16 files); and a few TS-policy or edge bugs (`o?.c.#f` gives 18030, `async function await(){}` in a script, `for ([x = 'x' in {}] of …)`, `for (let; ;)`, escaped `let` ASI). The binder adds 889 more false errors on sloppy code. No panics on any of the 53,616 files.
  EVIDENCE: test262.results.tsv FP listing; scanner.rs:2508-2546 (octal escape error regardless of mode), 2808-2830 (Octal_literals_are_not_allowed); grep for '<!--' finds no HTML-comment handling; Cargo.toml unicode-id-start '=1.1.2' comment
- [high] Newer syntax: `using` / `await using`, decorators (including accessor), import attributes, `import defer`, import.source()/import.defer() calls, #x in obj, string export names, logical assignment and hashbang all parse. Static `import source x from` does NOT parse at the pinned commit; upstream added it on 2026-10-02 in microsoft/TypeScript#63915. RegExp v flag, modifiers and duplicate named groups are supported only in the separate validator.

- [high] Literal fidelity. NumericLiteral.text is normalized to ToString(value): '9007199254740993' becomes '9007199254740992', '1e400' becomes 'Infinity', '017' becomes '15'. Because this is a round-trip string the f64 can be recovered exactly. BigInt text keeps its base prefix with separators removed ('0x1fn', '10n'). String text is cooked. Template head, middle and tail raw_text are plain source slices with CRLF not normalized. NoSubstitutionTemplateLiteral stores no raw text at all, so String.raw must be rebuilt from the source. Invalid escapes in tagged templates set ContainsInvalidEscape (cooked must be undefined).

- [high] No fail-fast and no depth guard. With a syntax error at byte 0, typescript.js still takes a full parse (52.7 vs 55.2 ms clean) because error recovery always builds the whole tree, and duplicate errors at the same position are dropped. Deep nesting has no guard: 20k nested [ or ( is fine, but 30k overflows the 8 MB main stack and aborts the process (cannot be caught).

- [high] No lazy or pre-parse of function bodies, and no API to re-parse one function from an offset. The only lazy mechanism (lazylist) is for member lists of .d.ts files: it parses fully, discards the nodes, and re-parses from a recorded position and context on first use. It shows the internals could support reparse-from-offset, but only through a fork.

It assumes strict mode and has no closure-capture, TDZ or eval/arguments-usage analysis. An engine still needs its own scope and variable-allocation pass, and that pass is the natural place for the missing early errors.

## Risks
- Fork drift: tsrs mirrors tsgo commit by commit and changes very fast (about 200 commits a week; parser internals were refactored many times in 3 weeks), so a patch set will conflict often.
- Memory safety by convention: everything is &'static and P is Send+Sync 'by decree'. Freeing a Region while a bytecode or debug structure still holds a P is use-after-free with no compiler help.
- Process abort paths you cannot catch: stack overflow on deeply nested input (crossed between 20k and 30k levels), a taken or exhausted 32 GiB reservation, and file-name and ScriptKind assertions. That is bad for eval of untrusted input in an embedder.
- License and identity: Apache-2.0 'derivative of TypeScript' with NOTICE obligations. Diagnostics are TS codes and English TS messages, not ECMAScript SyntaxError texts.
- JSDoc reparse in JS mode silently changes AST shape (cast wrappers, extra statements). Codegen that misses this will show up as subtle semantic bugs, not crashes.
- Lone-surrogate source text (from eval of JS strings) cannot be passed as &str; it needs a lossy or escaped transcode.
- Unicode identifier tables are pinned to TypeScript's (15.1), so they will lag ECMA-262's Unicode version.

## Open questions
- Does the TS checker's grammar code (check_grammar_*) cover most of the missing early errors? It is tied to Checker state (types, links, a Program), so lifting it out was not attempted or measured.
- Exact per-function memory and time cost of keeping AST regions alive for lazy compilation, compared with re-parsing whole files. Not measured.
- Would upstream accept a narrowly scoped 'engine mode' flag (no JSDoc reparse, no JSX for .js)? The docs say PRs are closed and the port must stay faithful, so probably no; not asked.
- Exact test262 numbers for lone-surrogate eval cases were not checked.
- Parse throughput against other Rust parsers is covered by the parser-perf workstream, not this one.
