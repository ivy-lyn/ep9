# spec-subsystems

## Summary
I checked every crate and engine below on 2026-10-20 against crates.io, the GitHub sources of V8 and Firefox, local clones, and experiments I ran myself. Spec status comes from tc39/proposals (commit of 2026-10-14). ES2026 adds upsert, JSON.parse source text access, Iterator.concat, base64 on Uint8Array, Math.sumPrecise, Error.isError and Array.fromAsync. ES2027 so far adds Explicit Resource Management, Temporal, Atomics.pause and the iterator additions (zip, chunking, includes, join). Decorators were moved back to Stage 2.7 in May 2026 and no engine ships them, so they should not be built now. Reuse is clearly right for Temporal (temporal_rs 0.2.6, which V8 links via temporal_capi), Intl (ICU4X 2.3.x, CLDR 48.2 / Unicode 17), Unicode case/normalize/properties (ICU4X), Number-to-string (ryu-js or dragonbox_ecma, both matched V8 on 400k doubles) and Math.sumPrecise (xsum). Some things must be built: toFixed/toPrecision/radix formatting, a Float16 conversion that rounds correctly, and the string representation. Rust's `{:.N}` formatting rounds ties to even, and the `half` crate rounds f64 to f16 wrongly on x86 and in its software path. RegExp is the big build-or-reuse call. regress (0.12.0) passes all v-flag, modifier and lookbehind tests in Boa, but it has no JIT and no Latin-1 input mode. It ran 1.7-7.8x slower than V8's JIT and roughly 0.8-5x slower than V8's own interpreter on my benchmark; SpiderMonkey reaches V8 speed by vendoring all of irregexp (~1 MB C++) behind a shim. BigInt: num-bigint and dashu are 2-4x slower than V8 on small numbers. V8's own bigint library (~200 KB, BSD) is the thing to port later. test262 at d53ebc8 has 53,616 tests, which is about 103k runs once strict and sloppy modes are counted. 4,660 of them expect a parse error and 109 use $262.agent, so the harness must run in one process, in parallel, with a watchdog and crash isolation per shard. Two concrete problems with tsrs for compliance: it pins unicode-id-start =1.1.2 (Unicode 15.1), which fails 16 test262 Unicode 16/17 identifier tests, and it cannot parse static `import source` (Stage 3).

## Recommendation
Build vs reuse, with rough effort in person-months (PM). Effort numbers are estimates.

1. RegExp. Put the regex engine behind an internal backend interface.
   - Phase 1: fork regress 0.12.0 and add a Latin-1 cursor plus a way to interrupt matching (0.5–1 PM).
   - Phase 2, once our JIT macro-assembler exists: port irregexp (compiler + bytecode + native backend, ~25–30k lines of C++, BSD) to Rust (6–12 PM), and keep a linear-time fallback for ReDoS. A cheaper middle step is to port QuickJS libregexp (3.4k lines of C, MIT).
   - Use tsrs's regexp validator or the regex engine's own parser for early errors. Do not add oxc_regular_expression as well.
2. Intl: ICU4X 2.3.x with baked data, plus icu_experimental for DisplayNames, RelativeTimeFormat, DurationFormat and units (9–15 PM to reach ~95% of intl402). Treat the data size (~5 MB for the full set) as a build option.
3. Temporal: temporal_rs 0.2.6 with timezone_provider, the same stack V8 uses (1–2 PM of glue). Use the same time-zone provider for Date's local time.
4. Numbers:
   - Number to string: ryu-js or dragonbox_ecma. Watch zmij-js; it is 3x faster but needs a -0 fix.
   - String to number: std parse for the float core.
   - Write by hand: the StringToNumber grammar; toFixed, toPrecision, toExponential and toString(radix) (port V8's dtoa pieces); and a correctly rounded f64→f16 conversion (do not use `half`). Total 1 PM.
5. BigInt: start with num-bigint or dashu (0.5 PM). Port V8's src/bigint onto GC-allocated digit arrays later (1.5–2 PM).
6. Strings: build our own Latin-1/UTF-16 representation with ropes, slices, thin/forwarding strings and atoms, following the V8 and SM designs (2–4 PM; core to performance).
7. Unicode: ICU4X properties, casemap and normalizer, with Latin-1 fast paths (0.5 PM). Patch tsrs to unicode-id-start 1.5.0 so all three Unicode sources are version 17.
8. Date: our own code, with a V8-compatible legacy parser (1–2 PM).
9. SharedArrayBuffer/Atomics: ecmascript_atomics-style inline asm, address-space-reserved growable buffers, a futex waiter list, and agents on OS threads (2–3 PM).
10. GC-coupled features to design in now: WeakRef/FinalizationRegistry (kept-objects list, ephemerons, cleanup jobs). Small builds:
    - Proxy/Reflect: 1–1.5 PM
    - Iterator helpers including zip and chunking: 1 PM
    - Explicit Resource Management: 1.5 PM
    - Float16 / sumPrecise via xsum: 0.5 PM total
    - ArrayBuffer/TypedArray including resizable and transfer: 2–3 PM
    - Modules (cyclic records, top-level await, attributes, JSON/text, import defer): 2–3 PM, plus a tsrs patch for `import source`
    - Engine ValueSerializer for structuredClone and workers: 1–1.5 PM
    - Stack traces, including the V8 stack-trace API for Node compatibility: 1–2 PM
11. Skip for now: decorators (Stage 2.7, no engine ships), ShadowRealm, immutable ArrayBuffer.

test262 harness (0.5–1 PM). Pin test262 like tsrs (gitignored checkout plus a file holding the hash).
- Index the front-matter once.
- Run in one process, in parallel (rayon on 18 cores): a fresh realm per test, harness files pre-compiled per worker (later from a startup snapshot), and both strict and sloppy runs (~103k).
- Support module, raw, async (wait for the Test262:AsyncTestComplete print after the event loop drains) and negative-phase checks.
- $262 hooks: createRealm, detachArrayBuffer, evalScript, gc, IsHTMLDDA, AbstractModuleSource, and agent tests on real threads sharing SAB memory.
- A watchdog interrupt per test. Sub-process shards so that a JIT crash or panic only loses one shard; then retry tests one at a time.
- A committed expectations file, so CI only reports differences.
- Target well under 60 s for a full run (estimate).

Runtime layer, on top of the engine:
- tokio event loop and timers.
- Microtask checkpoint after each task: Node's nextTick queue first, then promise jobs, then ClearKeptObjects, then FinalizationRegistry cleanup tasks.
- Unhandled-rejection tracking.
- Atomics.waitAsync timeouts.
- Module loader (oxc_resolver for Node resolution, CommonJS + ESM interop, TypeScript type stripping via tsrs).
- Workers with MessagePort.
- CDP inspector: Runtime, Debugger, Profiler and HeapProfiler domains (4–8 PM).
- Startup snapshots: needs a heap that can be relocated; decide this in the GC design now (2–4 PM).

## Risks
- RegExp speed: regress is 1.7–7.8x slower than V8's JIT on my microbenchmark. Reaching irregexp-class speed needs a native backend, and that depends on the JS JIT's assembler, so it comes late.
- Forking regress (Latin-1 cursor) or tsrs (Unicode 17, `import source`) creates maintenance cost against upstreams. tsrs does not accept outside PRs.
- The ICU4X Intl path tops out around 80% of intl402 today (Boa, Kiesel) because of ICU4X feature gaps (h24 hourCycle, locale canonicalization, parts of NumberFormat v3). Reaching V8/SM levels may need upstream ICU4X work.
- temporal_rs is still 0.x (0.2.6); the API may change between releases, although V8 depending on it lowers the risk.
- Data size: full ICU4X baked data is about 5 MB in the binary (segmenter alone ~2.4 MB). The embedding use case may need a lean build that loads data from a blob.
- Rust's memory model makes naive Atomics on SAB undefined behaviour. The inline-asm approach (ecmascript_atomics) is self-described as 'potentially unsound', has a single maintainer and is MPL-2.0.
- Small spec-precision traps (toFixed tie rounding, f16 double rounding, -0 formatting) can each cost a few hundred test262 failures if crates are used naively.
- Decorators, source phase imports and import defer are all still moving (decorators were just moved back). Implementing proposals early risks rework.
- Speed estimates for the test262 harness and the person-month figures are my extrapolations, not measurements.

## Open questions
- Does the user accept a C++ dependency for an interim irregexp FFI, as SpiderMonkey does, or must the engine be pure Rust? This decides between irregexp FFI, a Rust port of irregexp, and a libregexp port.
- Should the default build carry full ICU4X Intl data (~5 MB), or is a lean embedding build with data loaded at runtime required from day one?
- Node-compatibility goal: is the V8 stack-trace API (prepareStackTrace/CallSite), and with it V8-specific behaviour in Error.stack, required for the runtime?
- Will the user patch tsrs locally (unicode-id-start 1.5.0, `import source` parsing), or keep it as unmodified upstream and push these fixes downstream?
- I did not check xsum against Infinity/NaN inputs or every overflow edge case of Math.sumPrecise, and did not run regress over the full test262 RegExp suite directly; the conformance numbers come from Boa's integration.
