## Missing topics
- [constrains early design: true] Proper tail calls (ES2015 strict-mode PTC): No report raised this. 'Full test262' includes 35 tail-call-optimization tests. Only JSC (35/35) and XS (34/35) pass them; V8, SM, QuickJS, Boa, LibJS and Kiesel each pass 1/35 (test262.fyi features data in /private/tmp/claude-501/-Users-brooklyn-workspace-github-ep9/53ce3b1c-bc15-4f01-a4d1-8e97c5516415/scratchpad/work/engine-lessons/t262_meta.json). Supporting PTC changes the calling convention and frame layout: frames must be reusable for tail calls, interpreter JS→JS calls must not recurse on the Rust stack, and stack traces lose frames. It belongs with tiers' S0 frame-layout decision, or should be explicitly accepted as a gap, as V8 and SM do.
- [constrains early design: true] Startup snapshots and bytecode/code cache: Only spec-subsystems mentions it, in one line. Node and Deno start from V8 snapshots; V8 jitless relies on embedded builtins (tiers). Day-1 constraints: every heap→native pointer goes through an external-reference table; intrinsics are created deterministically; bytecode holds constant-pool indices, never raw pointers, so it can be cached and relocated. This can work with gc-design's non-moving heap if deserialization rewrites pointers.
- [constrains early design: true] Debugger/inspector (CDP) and async stack traces: Mentioned only as a 4–8 PM line item (spec-subsystems); there is no Rust CDP server to reuse (Hermes's is C++). Design constraints: a bytecode→source position table; ScopeInfo kept for closures and locals, which conflicts with dropping variables the optimizer thinks are dead; a breakpoint mechanism (op_debug bytecodes or a debug copy of the bytecode); the ability to deopt every JIT frame on attach; await/promise bookkeeping for async stacks.
- [constrains early design: true] CPU sampling profiler and heap snapshots: A sampler walks stacks from a signal or suspended thread across interpreter (VM-stack), JIT and Rust frames. That needs frame pointers everywhere and interpreter frames that can be found asynchronously, so it ties into tiers' frame-layout decision (tiers mentions only perf jitdump). Heap snapshots need heap parsability (gc-design already requires it) plus class or constructor names per object.
- [constrains early design: true] Stack overflow, OOM, termination and panic policy: JS recursion must throw RangeError. That needs stack-limit checks in every interpreter and JIT prologue, in recursive Rust builtins (JSON.stringify, join/toString on cyclic or deep arrays, regex backtracking), and in the parser. I verified that tsrs aborts at about 18.6k nested arrays and oxc at about 4.1k on an 8 MB stack, both uncatchable. Also needed: a heap limit with a near-limit callback (Node --max-old-space-size); TerminateExecution and interrupts, which can share gc-design's safepoint polls; and a Rust panic policy at JIT boundaries (extern "C-unwind" plus registered unwind info, or panic=abort).
- [constrains early design: true] Threading model: isolates, realms, workers: This is an open question in gc-design and nobody owns the decision. Choose isolate-per-thread with only SAB shared (V8), or a shared heap. Multiple realms per heap are needed early: $262.createRealm (test262 harness), Node vm.createContext, and later ShadowRealm. Intrinsics, shapes and ICs must be keyed per realm. tsrs's process-wide reservation and 1M source slots are shared by all isolates.
- [constrains early design: true] Security threat model and sandboxing: Gc-design S4 says 'decide the sandbox early' but no report made the decision. Running untrusted code in an embedding implies a V8-style sandbox (no raw off-heap pointers in heap objects; pointer tables), W^X and CFI on JIT entry points. Landscape: ~45% of V8 CVEs were JIT-related. Also, tsrs's abort paths (depth, reservation, file-name panic) make in-process eval of untrusted strings unsafe without a guard.
- [constrains early design: false] Fuzzing: Fuzzilli ships REPRL targets for JSC, V8, Spidermonkey, QJS, XS, Serenity (LibJS), duktape, njs and others (gh api googleprojectzero/fuzzilli/contents/Targets). ep9's shell needs a REPRL mode plus sanitizer coverage. Add cargo-fuzz for the parser front end, regexp and number conversions, and from S3 on, differential fuzzing between tiers and against node/QuickJS (tiers names this only as a risk). Cheap to add early, and does not shape the design.
- [constrains early design: true] Windows platform matrix: No report covered Windows on the engine side. The Win64 ABI has different callee-saved registers (rsi, rdi, xmm6-15), so the CSS spill trampoline differs. JIT code needs SEH unwind registration (RtlAddFunctionTable), and VirtualAlloc reserve/commit semantics differ. MMTk has no Windows support (#961 OPEN). tsrs compressed pointers are unix-only (tsrs_core/build.rs). A Node or Deno-like runtime must ship on Windows.
- [constrains early design: true] Cargo workspace integration of the pinned tsrs checkout, plus a patch workflow: This is the user's current request. I verified that ep9's root [workspace] must have `exclude = ["third_party"]`; without it the build fails with 'error inheriting edition'. tsrs's Cargo.lock and [profile] are ignored, its exact pins (unicode-id-start =1.1.2, icu_normalizer =2.3.0) enter ep9's graph and break or downgrade oxc and swc, and it needs rust-version 1.99. Every report expects engine patches, and upstream PRs are closed, so sync-tsrs.sh needs a patches/ step (or the hash file should point at a fork) and CI that re-applies patches whenever the pin changes.
- [constrains early design: true] Node compatibility layer (Node-API, Buffer, CJS, vm, V8-isms): Node-API is a fixed C ABI that Deno (ext/napi, Rust) and Bun (src/runtime/napi) implement on non-V8 engines (verified via gh). Its napi_ref, napi_wrap, finalizer and handle-scope semantics require an embedder rooting API, weak references with finalizers, and external-memory accounting. This is cheap with conservative scanning over a non-moving heap (Bun on JSC). The user deprioritized stable embedding API design, but if native addons are in scope, this ABI is fixed and is not ep9's to design.
- [constrains early design: false] WebAssembly: No report covered it. A runtime is expected to run npm packages that ship .wasm, and source-phase imports assume WebAssembly.Module. The MVP JS API can come later through wasmtime (Cranelift). Things that constrain early design: shared signal handlers (wasmtime traps via signals) and multi-GB memory reservations coexisting with tsrs's fixed 32 GiB range and the JIT's W^X. If WasmGC↔JS interop is a goal, wasmtime's own GC (gc-drc and gc-null features in its Cargo.toml) means two heaps with cross-heap cycles, where V8, JSC and SM use one unified heap.
- [constrains early design: true] Lazy compilation memory policy and bytecode flushing: The parser reports note that neither tsrs nor oxc can re-parse one function from an offset with its context, but nobody turned that into a policy. The choices are to keep AST arenas alive (about 4.6–6.8x the source size) or to re-parse whole scripts, and V8-style bytecode flushing needs one of them. This also covers keeping source text for Function.prototype.toString, and eval/new Function input, which is Latin-1 or UTF-16 and must be transcoded to &str for tsrs or oxc.
- [constrains early design: false] CI and performance-regression infrastructure: Parser-perf had to use instruction counts (proc_pid_rusage) because the machine's load average was 11–37. Track per-commit instruction counts and committed test262 expectation files, and run JetStream 3 JS workloads and v8-v7 nightly. Set this up in S0; it does not change the architecture.
- [constrains early design: false] Runtime conformance beyond test262 (Node test suite, WPT): test262 covers only the engine. Node-compatibility claims need node/test/parallel subsets, and web APIs (URL, fetch, streams, TextEncoder) need WPT, as Deno uses. This shapes the runtime roadmap, not the engine core.

## tsrs verdict
tsrs is not suitable as ep9's production JS parser in the form it ships. It is usable only as a short-term tree builder for bootstrapping, or as a permanently maintained fork.

What tsrs does well (verified):
- It parses valid JS: about 99.9% of valid test262 tests, no panics, compact 4-byte handles, UTF-16 column helpers.
- It handles about 4.5x deeper nesting than oxc before aborting.

What blocks it (verified in my spot-checks):
1. It catches only 26.8% of test262 parse-negative tests, or 34.5% with its regex validator and no false errors. Most early errors live in the 108k-line type checker.
2. The binder is unconditionally strict (binder.rs:1024, 2250), so it cannot be reused for sloppy mode or scope analysis.
3. The parser has no strict-mode, goal or target state.
4. It silently misparses `x = y <!-- z` with no error.
5. It always enables JSX in .js files.
6. In JS files it parses JSDoc eagerly and rewrites the AST (AsExpression and extra statements). This costs 2–4x on unminified, JSDoc-heavy sources and about 1.2–1.4x on minified bundles.
7. It rejects 42 valid programs:
   - legacy octal literals and escapes
   - Unicode 16/17 identifiers, because of the =1.1.2 pin, which also downgrades or breaks other crates in the same build
   - `a?.#x`
   - `let`/`await` used as identifiers
8. It does not parse static `import source`.
9. Process-global abort paths:
   - a fixed 32 GiB reservation at 0x4001_0000_0000
   - no depth guard
   - a panic on relative file names
10. The memory model is all &'static, so freeing a Region is safe by convention only; lone surrogates are stored as WTF-8 inside String.
11. It has no API to re-parse a single function lazily.
12. Upstream policy: PRs are closed, 'improvements are bugs', and churn is about 200 commits a week.

Every engine needs its own scope and closure analysis anyway, so the real extra cost of tsrs over oxc is:
- about 3,400 early-error checks, of which conformance estimates 52% are local AST checks and 35% need scope or strictness context
- a patch set of about 8 parser and scanner changes
- rejecting JSX and JSDoc nodes
- rebasing that fork against a fast-moving, faithful TS-Go port

The measured alternative is oxc_parser + oxc_semantic + oxc_regular_expression:
- 4653/4653 negatives and 99.98% positives
- 1.2–3.3x faster
- MIT licensed and accepts PRs

Its known gaps are about the same size or smaller than tsrs's: it aborts at about 4.1k nesting depth (issue #21953 open), has no eval-context API (#11793 open), has no lazy re-parse, and has heavy 0.x API churn, so pin it exactly.

Recommendation:
- Put oxc behind an engine-owned lowering boundary, i.e. lower to ep9's own IR and free the arena. Do not hold pointers into it as Nova does.
- Keep the tsrs pin, which the user's hash-file setup already handles (add `exclude = ["third_party"]` to the root workspace), for TypeScript type checking and tooling, ideally out of process so its exact dependency pins stay out of the engine build.
- The tsrs scanner (6.8k lines) is the most reusable piece if the team later writes its own V8-style parser.

If the user still chooses tsrs, these conditions are mandatory, not optional:
- a patches/ step in sync-tsrs.sh
- an engine-owned early-error and scope pass that never uses the tsrs binder
- a depth guard
- a decision on plain-ptrs vs the fixed reservation, made together with the GC heap cage

Confidence: high on the facts; the recommendation is a judgment call.
