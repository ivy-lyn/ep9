# tsrs-conformance

## Summary
I built a Rust harness that links tsrs_parser, tsrs_binder and tsrs_scanner by path, plus oxc_parser, oxc_semantic, oxc_allocator and oxc_span 0.155.0 (the newest on crates.io as of 2026-10-20). I ran every test under test262 language/, built-ins/ and annexB/ (48,635 tests; intl402 was run separately, 3,382 tests, and everything passed). The test262 checkout is d53ebc8b (2026-10-13). Each file was parsed as JS with ScriptKind::JS, with the right goal (Script, or Module via external_module_indicator force=true), and with a "use strict" prefix where the flags called for it. Untagged tests were run both sloppy and strict. Main result, parser only: tsrs passes 99.90% of positive tests (43940/43982) but only 26.78% of negative tests (1246/4653). oxc_parser alone passes 99.98% / 70.11%, and oxc_parser + semantic passes 99.98% / 100%; its 7 positive failures are tests oxc's own harness skips. Most early errors are not reported by the tsrs parser by design: it has no strict-mode state, it builds silent "missing" nodes, and TypeScript leaves early errors to the binder and checker. The binder can run on its own but treats all code as strict (as in TypeScript 7), so on sloppy-mode tests it reports errors that are wrong. Adding the binder (with tsc's own filter for plain .js files) moves negatives to 33.74% but drops positives to 98.54%; adding tsrs's own regex validator as well gives 41.44% / 98.47%. Of the 3,407 negative tests tsrs misses, about 52% could be caught by a local check on the tsrs AST, 35% need scope, strictness or function-context analysis, 11% are regex syntax, 3% are Script-vs-Module checks, and only 6 need a scanner change. The parser also rejects 42 valid programs, which do need parser or dependency changes. There were no panics or crashes in about 100k parses in either parser.

## Recommendation
If ep9 uses tsrs_parser, treat it as a fast, crash-free, error-tolerant tree builder, not as a checker of JS early errors. Plan an ep9 early-error pass that runs after parsing. Part of it can be a local AST walk; the rest belongs in ep9's own scope-analysis pass, which needs to track strictness and function kind. Validate regexes in ep9's regex compiler. Do not reuse the tsrs binder for early errors, because it treats all code as strict. Copying tsrs_checker's grammar checks is also costly, since they are tied to the type checker. Even with all of that, the 42 valid programs it rejects (Unicode pin, HTML comments, sloppy octals, a?.#x, `let`/`await` as identifiers, for-of `in`) need changes inside the parser or its dependencies. The user's PRs to tsrs are closed, so with the vendored copy this means keeping a fork. ep9 would also have to reject JSX nodes itself. As a reference, oxc_parser + oxc_semantic already gets 100% of negative and 99.98% of positive test262 tests with the same kind of parser + semantic split.

- [high] Main scores (language + built-ins + annexB; 43,982 positive / 4,653 negative; script 47,805, module 830). tsrs parser only: positive 43940/43982 (99.90%), negative 1246/4653 (26.78%), negative script 1216/4455 (27.30%), negative module 30/198 (15.15%), overall 92.91%. oxc_parser only: positive 43975 (99.98%), negative 3262 (70.11%), negative script 69.63%, negative module 80.81%, overall 97.13%. oxc_parser + semantic: positive 99.98%, negative 4653/4653 (100%), overall 99.99%.
  EVIDENCE: [artifacts/tsrs-conformance/results/summary.csv](artifacts/tsrs-conformance/results/summary.csv) (from scripts/analyze.py over results/results_merged.jsonl)
- [high] Other tsrs variants. Parser + tsrs's regex validator: positive 99.83%, negative 34.47%. Parser + binder with tsc's plain-JS filter: positive 98.54%, negative 33.74% (module negative 21.21%). Parser + binder + regex: positive 98.47%, negative 41.44%. Parser + unfiltered binder: positive 98.03%, negative 41.97%. Every variant passes all 3,382 intl402 tests.
  EVIDENCE: results/summary.csv. The regex variant re-runs Scanner::re_scan_slash_token(true) on each RegularExpressionLiteral, the same way tsrs_checker/src/grammarchecks.rs:131-156 does.
- [high] oxc numbers match oxc's published snapshot. Negative: 4653/4653, exactly matching tasks/coverage/snapshots/parser_test262.snap (snapshot taken at test262 7ab7fafa, pinned in oxc's .github/scripts/clone-parallel.mjs:13). The only 7 positive failures are annexB/language/expressions/assignmenttargettype/*, which oxc's harness skips (tasks/coverage/src/load.rs:99). Positive totals differ by about 18 because of the test262 commit difference and because oxc also counts test/harness (116 files).
  EVIDENCE: repos/oxc/tasks/coverage/snapshots/parser_test262.snap lines 1-6 ('Positive Passed: 47455/47455', 'Negative Passed: 4653/4653'). My manifest also has exactly 4653 parse-phase negatives.
- [high] Harness artifact found and fixed: tsrs pins unicode-id-start to =1.1.2 (Unicode 15.1) in its workspace Cargo.toml. In a combined build, Cargo then forces oxc onto the old Unicode tables too, and oxc failed 16 Unicode 16/17 identifier tests. I re-ran oxc in a separate oxc-only build (unicode-id-start 1.5.0), and those tests pass there. For an engine, this means depending on tsrs drags this pin into the whole dependency tree.
  EVIDENCE: third_party/tsrs/Cargo.toml ('unicode-id-start = "=1.1.2"'); `cargo tree -i unicode-id-start` shows 1.1.2 in the combined build and 1.5.0 in harness-oxc; results/results.jsonl (combined) vs results/results_oxc_only.jsonl
- [high] How to get tsrs parser errors: tsrs_parser::parse_source_file(SourceFileParseOptions{file_name, path, external_module_indicator_options:{jsx:false, force:is_module}}, text, ScriptKind::JS). Errors come from file.diagnostics() and file.js_diagnostics() (the latter covers TypeScript-only syntax used in a JS file, e.g. TS8010/8006/8013). jsdoc_diagnostics was always 0. The JS vs TS choice comes only from the ScriptKind argument: ScriptKind::JS sets NodeFlags::JavaScriptFile and turns off type arguments in expressions, so f<T>(y) parses as comparisons.
  EVIDENCE: tsrs_parser/src/parser_1.rs:213-219, 502-527, 754-771, 796; parser_3.rs:1645-1656 and 3473-3487; tsrs_ast/src/parseoptions.rs:65-96; checked by dumping the AST of snippets (`t262h dump`)
- [high] tsrs's JS mode always parses JSX: get_language_variant maps ScriptKind::JS to LanguageVariant::JSX, so `<div>{1}</div>` in a .js file parses with no error. No ScriptKind gives plain JS without JSX. No test262 file produced JSX nodes, so the scores are unaffected, but an engine would have to reject Jsx* nodes itself.
  EVIDENCE: tsrs_parser/src/utilities.rs:5-12; snippet dump showed JsxElement with no diagnostics; results/tests_with_jsx_nodes_in_tsrs_ast.txt is empty (all 48,635 files checked)
- [high] The tsrs parser ignores strictness completely, and the binder is always strict. Across 47,962 tests run both sloppy and strict, the tsrs parser result never changed (0 differences), and neither did the binder result. The parser has no strict-mode state. The binder runs check_strict_mode_* unconditionally (TypeScript 7 behaviour), so on sloppy positive tests it flags valid code: TS1101 'with' 297 runs, TS1100 eval/arguments 231, TS1212 reserved words 114, TS1102 delete identifier 90. It also reports TS2300 Duplicate identifier (198) and TS2451 (30, Annex B function-in-block code), and wrongly rejects labelled declarations (TS1344, 11) and await in a static-block function expression (TS1359, 4).
  EVIDENCE: tsrs_binder/src/binder.rs:1018-1025 (unconditional), 2250-2257; parser_3.rs:3192 ('Ignore strict mode flag because we will report an error in type checker instead'); ad-hoc analysis over results_merged.jsonl
- [high] In tsrs, most early errors are designed to be reported by the binder or checker, not the parser. tsc itself filters binder and checker output for a plain .js file to an allowlist of codes (plain_js_errors). Most of the missing checks live in tsrs_checker (108.7k lines; grammarchecks.rs is 3,615 lines with 61 check_grammar_* functions). The parser creates silent placeholder nodes, e.g. `throw\n1` becomes ThrowStatement(Identifier "") with no error.
  EVIDENCE: tsrs_compiler/src/program.rs:2704-2706 and 3825-3900; parser_1.rs:2232-2240 (comment: 'The actual error will be reported in the grammar walker'); grammarchecks.rs:1313, 1394, 2494, 2518, 2547; checker_06.rs:3384, 3537; snippet dump: `var [...x = 1]`, `([...x, y]) => 0`, `(a, b) = 1`, `f() = 1`, `label: break nolabel`, `super()` in a method all give 0 parser diagnostics
- [medium] The 3,407 negative tests tsrs misses, by where the fix belongs. (1) Local check on the tsrs AST, no scope info needed: 1759 (51.6%). This covers rest element/parameter rules 629, invalid assignment/destructuring targets 340, class-element rules (delete #x, static 'prototype', constructor modifiers) 238, import()/import.<name> forms 227 (tsrs builds a MetaProperty for any name, e.g. import.UNKNOWN), 'use strict' with non-simple parameters 110, declarations in single-statement position 92 (including `if (x) let\n[a]=0`), const/using/for-in-of declaration rules 77, and token/trivia checks such as a line break before =>, throw followed by a newline, and escaped keywords. (2) Scope, strictness or function-context analysis: 1189 (34.9%). This covers strict-mode-dependent rules 377, redeclarations 303, yield/await context 147, super() and super.x context 138, private-name resolution 105, arguments/await in class fields 60, labels and break/continue 33, new.target/return/import.meta context 18, and the module export table 8. (3) Regex syntax: 361 (10.6%); tsrs's own validator catches 358 of them. (4) Script vs Module goal and top-level position: 92 (2.7%), e.g. import/export accepted in a Script. (5) Needs a scanner change: 6 (LS/PS characters accepted inside a regex literal). oxc reports 2043 of these 3,407 in its parser and 1364 in semantic.
  EVIDENCE: results/tsrs_false_negatives_categorized.csv, results/tsrs_fn_categories.json (scripts/categorize.py classifies by oxc's error message; AST-only cases checked by `t262h dump` snippets)
- [high] Top tsrs miss clusters by directory: dynamic-import/syntax/invalid 227; expressions/assignmenttargettype 212; expressions/class/dstr 144; statements/class/dstr 144; built-ins/RegExp/property-escapes 142; module-code 137 (86 goal, 44 scope); literals/regexp 119; class/elements/syntax/early-errors/delete 96+96; block-scope/syntax/redeclaration 92; statements/for-await-of 91; class/elements (arguments in field initializer) 71+63; object/method-definition 69; switch/syntax/redeclaration 63. - [high] The tsrs parser wrongly rejects 42 valid tests, and these need parser or dependency changes: Unicode 16/17 identifiers 16 (the =1.1.2 pin); Annex B HTML-like comments 8; sloppy legacy octal literals and escapes 6 (TS1121/1489/1487/1488 always reported); private name in optional chain `a?.#x` 4 (TS18030, a TypeScript-only restriction); `in` inside a for-of head destructuring default 3; sloppy `let` as an identifier 2 (for(let;;), let); `await` as an identifier at script top level parsed as top-level await 1; `new import.meta()` 1; module top-level-await reparse `for(await {function(){}};...)` 1. The regex validator adds 32 more: Unicode 17 script values 22, and Annex B legacy regex syntax (\k, octal escapes, backreferences in non-u mode) 10.
  EVIDENCE: results/tsrs_false_positives.csv; e.g. language/statements/class/elements/private-field-after-optional-chain.js -> 'TS18030@1029'; annexB/language/comments/single-line-html-close.js -> 'TS1109'
- [high] No panics or crashes in about 100k parse runs per parser. Every call (tsrs parse, tsrs regex check, tsrs bind, oxc parse, oxc semantic) was wrapped in catch_unwind, and the orchestrator attributes crashes from B-marker lines. 0 panics and 0 abnormal exits for both parsers, with a 1 GiB stack.
  EVIDENCE: results/results.jsonl.events.json and results_oxc_only.jsonl.events.json are both empty ([]); a scan for panic/rx_panic/bind_panic/sem_panic fields found nothing
- [low] Rough speed side note, not a benchmark: summed per-file parse time over 99,979 runs was tsrs 0.75 s vs oxc 0.34 s (about 2.2x), with 16 workers running at once. test262 files are tiny, so fixed per-file setup dominates.
  EVIDENCE: 'us' fields in results/results.jsonl (Instant timing inside the harness)

## Risks
- The fix-location categories come from regex rules over oxc's error messages, plus manual AST dumps for a sample. Some tests in a cluster may need a different kind of fix.
- I did not run the full tsrs checker. I did not measure how many misses tsrs_checker (as tsc on a plain .js file) would catch; the static evidence is that many of the missing checks exist in tsrs_checker or grammarchecks.rs.
- test262 HEAD d53ebc8b (2026-10-13) differs from oxc's snapshot commit 7ab7fafa, so absolute positive counts differ by about 18 tests. Negative counts match exactly (4653).
- The combined build forces tsrs's unicode-id-start =1.1.2 pin onto oxc. Use the oxc numbers from the separate oxc-only build (results_oxc_only.jsonl / results_merged.jsonl), not the combined results.jsonl.
- tsrs on the user's machine is pinned to toolchain 1.99.1; the harness built with stable 1.99.1 from outside the tsrs workspace. No tsrs files were changed (git status is clean).
- The parser+binder score uses tsc's plain-JS allowlist (copied from program.rs). That reflects what tsc shows for a plain .js file, not what an engine would want.

## Open questions
- Should ep9 vendor tsrs at all if almost every early error needs a new pass? oxc_parser + oxc_semantic already does this at 100%. That is a product call for the user.
- How much of tsrs_checker/src/grammarchecks.rs (3.6k lines) could be pulled out without the type checker? I did not try.
- Would the tsrs maintainers accept JS-engine options upstream (plain-JS mode without JSX, a sloppy/strict switch, Annex B comments, a newer Unicode version)? Their PRs are closed to outside contributors, so a fork may be the only path.
- The tsrs binder's TS2300 Duplicate identifier errors on valid var/function redeclarations, and its 'always strict' behaviour: is either configurable in tsrs? Nothing I found suggests so (Binder::new takes only the file).
