## Context

- JS can patch prototypes, `Symbol.species` and `Promise.prototype.then` at any time. Fast paths and optimized code that assume the default must learn about a change. AOT code cannot be recompiled in place (02 §6).
- Enum objects are mutable at run time, so TS enum folds need a fuse [R16].
- A debugger can rewrite locals and bindings [R18]. H24 keeps PROVEN facts sound through two fuses.
- Depends on: H13 (stable indices: a builtin fuse is named by its stable index in units and snapshots; a dynamic fuse is named by a descriptor, C-01), H14 (dispatch-slot swap), H29 (lazy deopt), H17 (constness bits and replacement watchpoints), H24 (debugger fuses), H23 (interrupt polls).
- Depended on by: H30 (`Assume(fuse)`; fused HINTED facts), H32 (the "global invariant" row), H35 (fuse refs in the RW template), H13 (the fuse list is a stable index list).

## Decision

Copied from the plan row (02 §6): GuardFuse (explicit load + compare) and InvalidatingFuse (dependency → lazy deopt + dispatch-slot swap). Covers protectors, shape constness, TS-derived CHA and enum folds, the InspectorSession fuse (pops on session connect) and the DebuggerBindingWrite fuse (pops before a debugger writes a binding; deopts code that used PROVEN binding facts).

| Kind (04 §8) | In the code | On invalidation | Fast-path cost | Main use |
|---|---|---|---|---|
| GuardFuse | Explicit load + compare of a fuse word (RootIndex or link cell) | Code sees the new value and takes the slow path | One load + branch | AOT-jitless; any code that must not deopt |
| InvalidatingFuse | Nothing; a registered dependency | Lazy deopt of dependent frames (return-address swap) + dispatch-slot swap | Zero | JIT mode, hybrid; jitless where another entry exists |

- In AOT-jitless mode an InvalidatingFuse lazily deopts and swaps the slot to aot-baseline or interp; it patches no code (04 §4, 05 §10).

**As built (e719ffa).** No fuse registry exists. One T0 flag is a one-way invariant of the initial list: `ShapeState::proto_index` is set once a prototype-mode object gets an array-index own property (since M3-P0 also once a routed ARGUMENTS or MODULE_NAMESPACE object becomes a prototype, as its hooks may answer for an index) and is never cleared (V8's "no elements" protector; `crates/ep9_vm/src/shape.rs:287-292`, read by `shape::proto_index_keys` at `crates/ep9_vm/src/shape.rs:1461-1462`). While it is false, `[[Set]]` of a missing array element skips the prototype walk (`crates/ep9_vm/src/property.rs:489-494`). It is a Rust fast-path check, like a GuardFuse, with no stable index and no dependency list (H31-Q5).

**As built (fuse registry v0, 2026-10-28, M5-P1 FR0).** `crates/ep9_vm/src/fuse.rs`, per isolate in `Runtime::fuses`, Rust memory that holds no Value (handle-table indices, `Rc` fuse words, `Weak` code handles). (1) `FuseRef = Static(index) | Dynamic(Descriptor)` (C-01). (2) The static list is the builtins row and then the debugger row of the Decision list, in order, indices 0-10 (the iterators entry is four fuses: Array, String, Map, Set): Array species, Array iterator, String iterator, Map iterator, Set iterator, Promise.then lookup, no-elements prototypes, RegExp exec, TypedArray species, InspectorSession, DebuggerBindingWrite. A static fuse is usable only once the owner of its pop site wires it; v0 wires none, so each reads not intact and no code can depend on one (`proto_index` becomes the no-elements fuse in month 6, H31-Q5). (3) Descriptor kind 1 "prototype-chain validity by ProtoRef" guards the chain from the named prototype up to null; kind 2 "constructor chain by FunctionRef" guards the chain from the named function itself up to null (the guard of `x instanceof D` and of static loads on a derived class, which no ProtoRef names: MC-w15-9, V10-D12; no FACT_SCHEMA change).

**Registry v0: arming, dependents, reads and scope.** (4) `arm(descriptor, subject)` checks that the descriptor names the subject in the current realm (null, an intrinsic, a class constructor's proven initial prototype as `facts_export` proves it, a unit function or a table builtin; `ProtoRef::Unknown` names nothing), refuses a chain with a proxy (MC-w16-15) or deeper than `validity::MAX_DEPTH`, puts the chain's first object in prototype mode, and keeps its current VALIDITY_CELL by a strong handle and the subject by a weak one. `shape::note_change` invalidates that cell on a structural change of any object on the chain (H16 K5), and its fuse hook then pops the fuse. So the descriptor names the prototype and the registry keeps the dependents, never a cell that code binds (MC-w13-11). A dynamic fuse guards its chains from its first arm on. (5) Dependents are weak code handles: `depend` adds one, a pop marks each live one Invalidated (lazy deopt and the dispatch-slot swap come with H29 lazy deopt), and dead ones are dropped. The runtime sweep: after a GC, the next FinalizationRegistry cleanup point (`Cx::cleanup_finalization_registries`, which every microtask checkpoint runs) calls `Registry::sweep_after_gc`, which drops the dead dependents, the dead subjects, and every armed fuse that nothing uses (no live dependent and no fuse word held outside the registry) with its handles; a later `arm` makes such a fuse again. A heap weak source only notes the GC: the sweep cannot run inside it, because the heap's handle table is borrowed while the weak sources run. (6) The GuardFuse read: `guard` gives the fuse word, `intact` reads it (one load and one compare; the word stays Rust memory until a root table or a unit link cell names it, H31-Q3). (7) Pops are one-way: a popped word never reads intact again, and a popped subject is refused by `arm` and `guard` for the life of the isolate (the popped list holds it weakly). (8) Scope (H31-Q2; M5-P2 CONSTREP, M5-P1-ORCH-13): one GuardFuse word per armed subject (`Subject` holds the word; before M5-P2 one word per descriptor). Kinds 1-2: the dependents are per isolate, so a pop of any subject, in any realm, invalidates the dependents of every subject of the descriptor (doc 13 §3.5) and puts the descriptor in the "popped in any realm" summary, which refuses `depend` from then on; the other realms' words stay intact, and their subjects still arm and read. Code that runs against another subject of the same name (another realm's intrinsic, another closure's class prototype) arms the fuse with that subject, which gets its own word. `depend`, `guard` and `intact` of a dynamic fuse take the caller's subject and refuse one that no arm names or whose state changed (`NotArmed`: kinds 1-2, the subject's current validity cell, read with no new cell made, is not the one its arm kept; kind 3, its field bits are not the ones its arm read), so a word never answers for a subject nothing watches (M5-P1 review). (9) Kind 3 "field constness and representation" (M5-P2 CONSTREP, C-02, H17 rep/const row): `Field { index }`; its subject is a fast shape that has descriptor `index` as a data property, and the arm keeps the field's owner (`shape::field_owner`, the shape that added it), so every shape of the field's family names one subject. A widening of the field's representation or const bits (`field_rep.rs`) writes every DESCRIPTORS cell of the family in place and pops it (`fuse::on_field_change`). A shape is run-local, so a kind-3 subject is the realm's own and its dependents are its subject's only (a pop invalidates no other family's code). A compiled kind-3 read needs no new word: it loads the field's details through the shape (SHAPE +24 DESCRIPTORS) and compares bits 4-7 with the bits it was compiled for, which only widen (H17 rep/const row); the Rust word mirrors it. No edit of `shape.rs` or `property.rs` (V10-D13); FUSE kind 83 stays reserved (no fuse cell needed). Tests: `tests::fuse` (a pop invalidates every dependent; a dead dependent is dropped; a proxy chain is refused; the name checks; the constructor chain; two realms, and a read for a subject no arm names; collections; an unused fuse goes at the cleanup point after a GC; the static order)

## Consequences

- **Gains.** Zero-cost invariants in JIT code (InvalidatingFuse). A cheap, deopt-free check in AOT-jitless code (GuardFuse). One mechanism for builtins, shapes, TS facts and the debugger.
- **Costs.** Every fast path must name its fuse. A pop deopts all dependent code at once; a program that patches a builtin early pays it once.
- **Follow-ups.** Build the registry (M1-M2). The fuse list joins the H13 index lists. H32 picks GuardFuse or InvalidatingFuse per mode.
