## Context

- Every tier and code kind deopts to bytecode, and units ship it (H35 bytecode section). So the bytecode is an ABI between BytecodeGen, T0, T1, T2, the deoptimizer and both AOT kinds.
- The same bytes serve the code cache and AOT units (H1). Determinism lets CI compare builds by hash.
- SP-Dispatch (H15) proved the DSL style: one opcode list, expanded per dispatch method. This ADR fixes the list itself.

## Decision

Copied from the plan row: register + accumulator, 1-byte opcodes, wide prefixes, feedback-slot operands, relative jumps, side tables, constant-pool indices only, `TailCall` reserved. Deterministic generation (same decoded source + flags + ABI version → same bytes), content hash, versioned ABI, serialized liveness (not in v0: H02-Q1). Bytecode offset = the only deopt/OSR id. Stable function id = preorder index. Units ship bytecode of every compiled and inlined function. [2026-11-04, M6-P3 B1W; FREEZE-M1 B1; MODES-CHECK MC-w20-O2, MC-w22-O6; doc 13 §3.2 "Counter sessions":] "Flags" in the determinism rule means the source flags (the code kind, strict and the TS flags: header offset 20, bits 0-2 and 8-15) and the two `CompileOptions` fields: `embed_source` changes the bytes and the content hash (`source_roundtrip.rs` `embed_source_false_gives_none`); `engine_build_id` changes the bytes but not the content hash (F12; `determinism.rs` `content_hash_excludes_build_id_and_covers_ts_flags`). The gate is the Rules row "Same builder input → same bytes and hash". No execution policy (`ExecPolicy`, `ExecOptions`, a preset, the feedback mode) and no session (a debugger, coverage or a profile run) changes the bytes BytecodeGen makes, so one unit serves every preset (H35). No session changes a fold, and no fold decides the module kind: the embedder picks script or module (`compile_module`; the CLI flag `--module`), never the source text. Check today: a grep for `ExecPolicy`, `ExecOptions` and `ics_only` over `crates/ep9_frontend`, `crates/ep9_bytecode` and `crates/ep9_regexp` prints nothing (at 39788b53). A counter session that needs other code joins the codegen-flag hash (doc 13 C-18), never the bytecode. "Serialized liveness" is H02-Q1: v1 computes the liveness and serializes none (the H02-Q1 fill).

The format decisions below fill the gaps the plan leaves (kind **fill**).

## CompiledUnit v0 layout

All integers little endian. Header 168 bytes (ABI 5; 160 in ABI 1-4); then 6 sections back to back (5 in ABI 1-4). Bytes 0..20 are a frozen prefix for every ABI version. [2026-11-04, M6-P3 B1W; FREEZE-M1 B1; doc 13 C-12, F-R1:] The hints section (index 4, flag bit 17) stays in ABI 5 and stays empty. No v1 writer fills it: BytecodeGen never calls `UnitBuilder::set_hints` (only the `ep9_bytecode` round-trip tests do, so the reader stays checked), so a unit has flag bit 17 = 0 and a hints section of length 0, and the reader refuses hint bytes without the flag. Facts travel beside the CompiledUnit, never inside it: their one home is the container `facts` section (the `ep9_unit` section kind 6, `Hints` today; H35). Why: the content hash covers the hints bytes (every byte but the hash and the build id), so a unit with hints would never have the hash of its training profile's unit (doc 13 F-R1).

| Offset | Size | Field |
|---|---|---|
| 0 | 8 | magic `89 45 50 39 42 43 0D 0A` ("\x89EP9BC\r\n", PNG-style) |
| 8 / 12 / 16 | 4 each | ABI version (5) / header size (168) / total size |
| 20 | 4 | flags: bits 0-1 code kind (script, module, eval); 2 strict; 8-15 TS ([H03](H03-ts-runtime-semantics.md)); 16 has source; 17 has hints |
| 24 / 25 | 1 / 7 | hash algorithm (1 = SHA-256) / reserved, zero |
| 32 / 64 / 96 | 32 / 32 / 16 | content hash / source hash / engine build id (not hashed) |
| 112 / 116 | 4 / 4 | source length in bytes / reserved, zero |
| 120 | 48 | section table: (offset, length) for strings, scopes, functions, source, hints, module records (index 5, ABI 5) |

Check order: magic, ABI version, header layout, content hash, then structure, then the verifier. The ABI version comes before the hash, so a unit of another ABI ends in SOURCE even if a later ABI changes the header or the hash rule. For a code-cache entry, SOURCE and LOAD ERROR both recompile the source file.

Function record: kind, flags, name, parent, outer scope, source start/end, parameter count, `length`, register count, then bytecode, constants, feedback kinds, handlers, positions (each with a u32 count), then (ABI 5) the mapped-parameter list: scope id + 1 (0 = no list) and a u32 count of slot entries, each a context slot + 1 (0 = a parameter that a later duplicate name shadows). Optional ids store `id + 1` (0 = none). `tests/golden/tiny-unit.hex` pins the bytes.

**Module records (section 5, ABI 5).** Empty for a script or eval unit; never empty for a module unit (the verifier checks both). It holds the records of ECMA-262 §16.2.1.6 ParseModule, every list in source order: a flag byte (bit 0 = `[[HasTLA]]`); the requested modules (specifier string id, then (key, value) string id pairs of the import attributes, sorted by key in UTF-16 code unit order, keys unique; one entry per distinct pair of specifier and attributes); the import entries (request index, import name string id + 1 with 0 = namespace-object, local name, module cell i32); the local export entries (export name, local name, module cell); the indirect export entries (export name, request index, import name string id + 1 with 0 = `all`); the star export entries (request index). The export entries are sorted as ParseModule step 10 does: a re-export of an imported binding is indirect, a re-export of an imported namespace object stays local. Module cells are the BytecodeGen v0 numbering (exports `1, 2, ...`, imports `-1, -2, ...`); the verifier checks only that a cell is not 0. The import phases of the stage 3 proposals (`import source`, `import defer`) are not recorded. `tests/golden/sample-module.txt` shows every kind.

**Entry-frame rule (SP-Dispatch lesson).** The spike's entry function had no caller header, so `Return` from it read garbage. In ep9 the host entry writes a full H14 header, so `Return` from function 0 returns to the host. The verifier enforces the bytecode side: only function 0 has an entry kind (= the unit's code kind); it has 0 parameters and no `CreateMappedArguments`, `CreateUnmappedArguments`, `CreateRestParameter` or `LdaNewTarget`; it is never a closure target.

**Runtime id 41 with the hole (as built, M3-P2 ASYNCGEN).** `CreateAsyncFromSyncIterator(iterator, next)` with `next` = the hole means GetIterator(iterator, async) (§7.4.3): the VM calls `@@asyncIterator` and, when it is undefined or null, makes an async-from-sync iterator over `@@iterator` (`ep9_vm` `interp/slow/async_gen.rs`, AG3). With any other `next` it is CreateAsyncFromSyncIterator of the Iterator Record (`iterator`, `next`) as documented. BytecodeGen emits only the hole form, for `yield*` in an async generator and for `for await` (`bytecodegen/async_gen.rs` `get_async_iterator`, AGF5), because ABI 5 bytecode cannot load `@@asyncIterator` (no symbol constant; a global `Symbol` lookup is observable). The hole is never a JS value, so the two forms cannot mix. Arity 2 does not change; no ABI change.

**Module function 0 (as built, M3-P2 MODULE step 2, M3-P2-MODULE-F0).** Function 0 of a module unit has the `ASYNC` flag, the only generator-capable flag that `flags_fit_kind` allows for a `Module` function. It starts with `SwitchOnGeneratorState`, runs InitializeEnvironment's own part (the module's functions, `var` cells set to undefined, TDZ holes), and suspends with `SuspendGenerator` at suspend id 1; resumed, it runs the statements (`bytecodegen/module.rs`). The VM never calls it: Link makes its closure (context = the MODULE record) and a generator object for it, gives that object as the receiver (the entry-frame rule above forbids `LdaNewTarget`), and resumes it twice: to suspend id 1 in InitializeEnvironment, then to the end in Evaluate (`ep9_vm` `module.rs`). The prologue moves the receiver to a register and makes `this` undefined. The verifier does not check this contract; the VM refuses a module function 0 without the `ASYNC` flag (an internal error, "module function 0 is not resumable").

## Consequences

- **Gains.** BytecodeGen gets a typed builder; the VM gets a verified unit it can decode without bounds checks. Units and the code cache share one canonical format.
- **Costs.** Load speed on Apple M5 Max, 6.7 MB of random units, release: hash 440 MB/s, hash + decode 295 MB/s, + verify 184 MB/s. Portable SHA-256 is 422 MB/s; hardware SHA-256 (OpenSSL) is 3,316 MB/s. The hash is about 40% of load time.
- **Follow-ups.** BytecodeGen (01 §5); interpreter DSL on `for_each_opcode!` (H15); determinism CI on the corpus; ADR index update.
