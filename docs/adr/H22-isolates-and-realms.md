## Context

- D14 (decided 2026-10-20): isolate per thread; only SharedArrayBuffer memory is shared. A shared heap would need a cross-thread safepoint protocol and cross-thread barriers [R09].
- Realms are needed early: `$262.createRealm` is in 284 test262 files (d53ebc8b: built-ins 167, staging 78, language 19, intl402 11, annexB 7, harness 2), and Node needs `vm.createContext` [R08].
- AOT: unit text is shared per process; unit RW data is copied per isolate; realm values come through IntrinsicRef by stable index (05 §8, H13).
- Depends on: D14, H7 (cage, code range), H10 (CSS), H13 (stable indices). Depended on by: H11 (no cross-thread barrier), H20-Q2 (realm of a builtin), H23 (termination), H25 (SAB), H35 (RW copy per isolate).

## Decision

Isolate = one heap, one thread at a time; N realms; workers are isolates; only SAB memory shared. Unit text shared per process; unit RW data per isolate; realm values via IntrinsicRef (02 §6).

```text
 process
   code range (one per process; to be built before Spike B, H7): JIT code + unit text (RX)
   isolate A (thread 1)                      isolate B (thread 2)
     cage A: heap pages (64 GiB VA)            cage B
     VM stack, roots, atoms, units             ...
     realm 0..n (REALM records; the current one's values in the roots)
   SAB backing stores: off heap, shared (H25)
```

## Rules

| Rule | Check | From |
|---|---|---|

## Consequences

- **Gains.** No cross-thread barrier or safepoint (H11 keeps one barrier). The CSS range check rejects every cell of another isolate. Dropping an isolate releases its whole cage.
- **Costs.** Each isolate reserves 64 GiB of address space by default, plus 128 MiB once per process for the code range (H07). At most 2,046 default cages fit below 2^47 (H07 Costs), fewer when the code range or other mappings take slots. Workers copy data, except SAB memory.
- **Follow-ups.** The process code range (H7, before Spike B). A smaller cage for workers (H22-Q8, M3). Realms are built (M0 month 3, H22-Q3). The realm of a promise job is settled for both jobs (X-REALM3, X-R2-1): the Job of NewPromiseResolveThenableJob runs in GetFunctionRealm(then) (§27.2.2.2), and the Job of NewPromiseReactionJob runs in GetFunctionRealm(handler) when the handler is not empty, else in the current realm (§27.2.2.1; H22-Q10, fixed in M3-P3 fix round 2). So an error that a reaction job makes before its handler runs is made in the handler realm: for example, with `vm_stack_slots` 1024, a bound handler of another realm with 1,100 bound arguments rejects with a RangeError of the handler realm (`push_bound_args`, from `call::call_with`, throws before `realm::enter_realm_of`), as node v24.22.1 does.

These records stay in the map as retryable `new` records, and no failed completion is kept. On a later `Cx::run_module`, each request that has no module yet (an empty `[[LoadedModules]]` entry) calls the host `resolve` hook again, and the `load` hook when the realm's map has no module of that name; a request that has its module keeps it, and a module in the map is not loaded again. So when the host now gives a valid module, the graph loads, links and runs; when the host gives the same failure again, the entry fails again with that error (ES2025 HostLoadImportedModule needs the same result again only for a load that succeeded).
