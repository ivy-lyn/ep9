## Context

- D14 (decided 2026-10-20): isolate per thread; only SharedArrayBuffer memory is shared. A shared heap would need a cross-thread safepoint protocol and cross-thread barriers [R09].
- Realms are needed early: `$262.createRealm` is in 284 test262 files (d53ebc8b: built-ins 167, staging 78, language 19, intl402 11, annexB 7, harness 2), and Node needs `vm.createContext` [R08].
- AOT: unit text is shared per process; unit RW data is copied per isolate; realm values come through IntrinsicRef by stable index (05 §8, H13).
- Depends on: D14, H7 (cage, code range), H10 (CSS), H13 (stable indices). Depended on by: H11 (no cross-thread barrier), H20-Q2 (realm of a builtin), H23 (termination), H25 (SAB), H35 (RW copy per isolate).

## Decision

Isolate = one heap, one thread at a time; N realms; workers are isolates; only SAB memory shared. Unit text shared per process; unit RW data per isolate; realm values via IntrinsicRef (02 §6).

```text
 process
   code range (one per process; to be built before Spike B, H7): JIT code + unit text (RX)
   isolate A (thread 1)                      isolate B (thread 2)
     cage A: heap pages (64 GiB VA)            cage B
     VM stack, roots, atoms, units             ...
     realm 0..n (REALM records; the current one's values in the roots)
   SAB backing stores: off heap, shared (H25)
```

## Rules

| Rule | Check | From |
|---|---|---|
| An isolate runs only on the thread that made it | `Isolate` is not `Send` (compiler) | M0 wk3 |
| Each isolate owns one cage; no cell of one isolate is a root of another | `Heap::new` reserves its own `Cage`; `find_cell` reads only its own chunks | M0 wk2 |
| `TerminateHandle` is the only cross-thread entry into an isolate | `terminate_from_another_thread` (every dispatch kind) | M0 wk3 |
| A `Value` never moves from one isolate to another | Embedder contract; no check yet (H22-Q9) | M0 wk3 |
| JIT code and unit text live in the process code range; unit RW data is copied per isolate | Spike B, SP-Unit; H35 load step 6 | before Spike B |
| AOT code reaches realm values only through IntrinsicRef | H35 zero-relocation check (A2) | A2 |

## Consequences

- **Gains.** No cross-thread barrier or safepoint (H11 keeps one barrier). The CSS range check rejects every cell of another isolate. Dropping an isolate releases its whole cage.
- **Costs.** Each isolate reserves 64 GiB of address space by default, plus 128 MiB once per process for the code range (H07). At most 2,046 default cages fit below 2^47 (H07 Costs), fewer when the code range or other mappings take slots. Workers copy data, except SAB memory.
- **Follow-ups.** The process code range (H7, before Spike B). A smaller cage for workers (H22-Q8, M3). Realms are built (M0 month 3, H22-Q3). The realm of a promise job is settled for both jobs (X-REALM3, X-R2-1): the Job of NewPromiseResolveThenableJob runs in GetFunctionRealm(then) (§27.2.2.2), and the Job of NewPromiseReactionJob runs in GetFunctionRealm(handler) when the handler is not empty, else in the current realm (§27.2.2.1; H22-Q10, fixed in M3-P3 fix round 2). So an error that a reaction job makes before its handler runs is made in the handler realm: for example, with `vm_stack_slots` 1024, a bound handler of another realm with 1,100 bound arguments rejects with a RangeError of the handler realm (`push_bound_args`, from `call::call_with`, throws before `realm::enter_realm_of`), as node v24.22.1 does.

| H22-Q3 | What is a realm? | M1 | **Filled 2026-10-23 (M3-P1 REALMS): as built.** A realm is a REALM record (OBJECT_LAYOUT 3: global object, global lexical record, intrinsics list indexed by `IntrinsicId`, the H13 stable index; IntrinsicRef = `realm.intrinsics[j]`). Each function stores its realm (`[[Realm]]`, FUNCTION +48). The current realm is `Cx.realm`, and its values are in the runtime roots, the builtin intrinsic slots and `%Symbol.prototype%`, so no reader of a root takes a realm argument (V8-A10). A call of a function of another realm switches: `realm::switch` loads the callee realm's values from its record and puts the caller's back on return or throw (`call::call_host`, `call::call_function_object`, `call::run_resumed`, the Job of NewPromiseResolveThenableJob in `abi/jobs.rs`, which runs in GetFunctionRealm(then) as §27.2.2.2 says (X-REALM3), and the Job of NewPromiseReactionJob there, which runs in GetFunctionRealm(handler) when the handler is not empty as §27.2.2.1 says (X-R2-1); T0 `call_fast` sends such a call cold for one compare, and `slow::call` runs it nested: one Rust level per cross-realm call). Per isolate, shared by all realms: atoms, well-known symbols, the symbol registry, the identity-hash key (H12-Q1), shapes, FunctionInfos. `realm::switch` empties the function shape caches (`shape::clear_realm_caches`: the plain, generator, async and async generator function shapes), so they keep no other realm live. A function's lazy `prototype` object uses the intrinsics of the function's `[[Realm]]` (`exotic::function_prototype`). Under `spike-native`, native and (b) code runs in its function's realm too (`native::call_in_its_realm`; `call_any`, `call_from_rust` and `run_b` switch). Known limit: `builtins::existing_function` knows the first realm's builtin functions only, so its fast paths take their spec steps in a later realm. Each realm has its own module map (M3-P2 MODULE): the realm's `[[HostDefined]]` (`realmf::HOST_DEFINED`) holds an ELEMENTS list of (name, MODULE record) pairs (`crates/ep9_vm/src/module.rs`, `map_get` and `map_add`), so a module name that the host loads (its `load` hook gives a unit) gets one record per realm and links and runs once per realm, and a module of one realm never binds to a module of another. `Cx::run_module` uses the map of the current realm (`Cx.realm`); a new realm's field is undefined, and the first module load in it makes the list. A load that fails leaves no half-loaded record that a later entry trips on (M3-P2 fix round 2, X-MOD3), and it is not a cached load error: `load_graph` walks every reachable record that is still `new`, also one that is in the map already, and when a load fails it sets each record that it marked back to `new`. These records stay in the map as retryable `new` records, and no failed completion is kept. On a later `Cx::run_module`, each request that has no module yet (an empty `[[LoadedModules]]` entry) calls the host `resolve` hook again, and the `load` hook when the realm's map has no module of that name; a request that has its module keeps it, and a module in the map is not loaded again. So when the host now gives a valid module, the graph loads, links and runs; when the host gives the same failure again, the entry fails again with that error (ES2025 HostLoadImportedModule needs the same result again only for a load that succeeded). A cached evaluation error is different: a module whose Evaluate threw keeps its `[[EvaluationError]]`, and each later entry that needs it throws that error again, with no new hook call and no new run of its body. A termination during Evaluate (H23) gives each module on the evaluation stack an engine-internal status, `status::ABORTED` (not a spec status; X-MOD2): a later Evaluate that reaches such a module throws an Error ("the evaluation of module <name> was terminated") and never takes the module as evaluated, and Link takes it as evaluated |
