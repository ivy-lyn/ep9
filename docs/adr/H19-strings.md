## Context

- Goal: string speed of the V8 and SpiderMonkey class [R06]. Property keys, shapes and ICs compare one word, so a key must be one cell per text.
- G6: hostile input must not degrade the engine (hash flooding, huge strings).
- Depends on: H6 (cell values), H8 (word0 kind byte and flags), H10 (CSS keeps interior pointers), H12 (no address hashing), H13 (stable atom indices). Depended on by: H17 (shape keys), H20 (the builtin read API), H35 (units name atoms by index).

## Decision

SeqLatin1, SeqUtf16, rope (length ≥ 13), slice (length ≥ 13), thin, external. Atoms with a cached hash and an array-index bit. Never a Rust `String` as the JS representation. Snapshot atoms use H13 indices (02 §6).

- **Why a `JsStr` is safe in VM code.** The heap never moves cells (S0-S2), and the conservative scan keeps a cell alive from an interior pointer (`find_cell`, `crates/ep9_heap/src/trace.rs:931`). So a view held in a Rust local stays valid across an allocation. The borrow rule (`view` borrows `&Cx`) protects builtins, which get no `&Runtime` (H20 `abi::Cx`), and a future moving GC (S3) [I49].
- **The embedder view.** `Isolate::string_view` does not root the string, and the embedder can keep a view where the conservative scan does not look (a `Vec`). So it borrows the isolate with `&mut self`: no isolate call runs while the view lives. A shared borrow is not enough, because a `&self` call can allocate or collect: in the in-crate tests and the spike-native build, `Isolate::heap` (`Heap::collect`, `Heap::alloc`, `Heap::alloc_shape`). The raw `Isolate::global` (it interned its name) was one more until M3-P3 removed it, and the default build has no `Isolate::heap` since M3-P3 fix round 5 (H20-Q4). A raw `Value` is not a root, so `string_view` also checks it before it reads it: it reads only a live string cell of this isolate's heap (`Heap::is_cell`), and gives `None` for a freed cell, a cell of another heap or bits that do not start a cell (H20-Q4, Codex W4-1).
- **GC rule** (W4-GC-RULES). The weak source holds an `Rc` clone of the table and borrows it during a GC. Interning never holds a borrow across an allocation: it allocates first, then borrows and inserts. A held borrow makes the GC panic ("borrowed across a GC point").
- **Why only CONS and SLICED cells become THIN** (M4-P2). A THIN cell writes the atom at +16. In a CONS or SLICED cell, +16 holds a pointer, and a `JsStr` of that string reads another cell (a leaf or the parent), which the view keeps alive (conservative scan of interior pointers). In a SEQ cell, +16 holds the code units that a live `JsStr` may still read, and a SEQ cell under 24 B has no room. All three kinds are 32 B, so the heap stays parsable when the kind byte changes.
- **Why the number cache lives in Rust memory** (rule 8, M4-P2). Its strings are not roots and are never read after a GC: the weak source bumps the epoch at every collection, before the sweep, and an entry of an older epoch counts as empty. So the cache never holds a Value across a collection, and it costs O(1) per GC.

- **Why a PRNG and not a counter.** A counter makes hashes of symbols made in a row adjacent, which clusters them in a power-of-two hash index. H12-Q3 proposes a per-isolate PRNG; V8 also takes symbol hashes from the isolate's random number generator. The seed follows the string hash seed, so a run with `EP9_HASH_SEED` is reproducible.
- **Why the registry is strong.** `Symbol.for(k)` must return the same symbol for the life of the realm, and a program can observe identity (`===`) even when it holds no reference in between. A weak registry would need the "symbol can be held weakly" rules of §9.13 CanBeHeldWeakly; registered symbols cannot be.

## Consequences

- **Gains.** A key compare is one word for atoms, the same in T0, ICs, JIT and AOT. Strings save 8 B against the week-3 header. `s.length` is one load for every kind, ropes included. Index keys stay strings, so property.rs needs no number-key path this week.
- **Costs.** Every unit string and computed key pays one hash and one table probe (a rope or slice key pays it once, then forwards). Every GC walks the atom table (O(capacity)). A number-string cache miss costs about 60 instructions (strings-m1 `concat-rope` +1.9%). A text over the limit built from Rust (for example an error message that quotes a huge key) becomes `<error>`, as in V8 (H19-Q5).
- **Follow-ups.** Ropes and slices are built (M4-P1) and thin strings (M4-P2); the H19-Q2 lookup without insert is not built (`atoms::lookup` is test-only; month 5); external strings; P2-OBJ calls `intern_key` on define paths so stored keys are always atoms; symbol keys in `probe` and `key_hash` (done, see "Symbols"); `===` of two atoms can skip the content compare (`conv.rs`, `interp/ops.rs`).

| H19-Q1 | When does a rope flatten (index, compare, atomize)? | M1 | V8: flatten on index and on atomize. **Filled 2026-10-27 (as built, M4-P1 STR1 and M4-P2 STR2; V9-D13):** a CONS flattens in place, once: it becomes (flat, ""), so a second flatten allocates nothing. Flatten runs on index (`char_at`, `Cx::flatten` before a builtin reads units), on atomize (`atoms::atomize`, used by ToPropertyKey) and before every `view`. Compare, equality, hash and `array_index` never flatten: they walk the rope and allocate nothing on the JS heap. | H19-Q2 | Atom lookup without insert for [[Get]] | M1 | Probe only; a miss means "no such key". **Filled 2026-10-27 (Draft proposal, M4-P2 STR2; not built):** a [[Get]], [[HasProperty]] or `in` with a string key that is not an atom probes the table and never inserts. A miss means no object has the key (stored keys are always atoms, `intern_key`), so the lookup ends as "absent" and makes no atom; a hit gives the atom (and a CONS or SLICED key becomes THIN). The probe exists as `atoms::lookup` (test builds). The caller is the keyed slow path (`interp/slow`, `property.rs`), which no string role owns: the keyed role (M4-P3) or the month-5 plan builds it. **Note 2026-10-27 (M4-P4 fixer B, Codex H19 H-2):** a miss shows only that no stored key has the text. Array elements (`object::array_set` stores no key), String wrapper indices (`wrapper::string_own_property` makes them) and the routed kinds (arguments, module namespace, proxy: their hooks answer) have properties with no atom, also as prototypes. So the shortcut may end a lookup as absent only when the key is not an array index (`key::array_index_of`) or no object on the chain can hold an index without a key (no array, no String wrapper, no routed kind; `shape::proto_index_keys` is false for the chain), and never past a routed kind on the chain. Owner: the month-5 plan row that builds it (VM lead role). | H19-Q4 | Thin strings: when can a string not become an atom in place? | M1 | Ropes and external strings get a thin forwarder. **Filled 2026-10-27 (as built, M4-P2 STR2):** a SEQ string becomes the atom in place (ATOM flag) when its text has no atom, and stays as it is when one exists. Through `atomize`, a CONS or SLICED string never becomes an atom: a CONS is flattened and its flat part becomes (or finds) the atom; a SLICED text with no atom is copied into a SEQ atom, so no atom keeps a large parent alive. The CONS or SLICED cell then becomes THIN (kind 5, +16 the SEQ atom): the next atomize is one load and the old parts or the parent can die. | H19-Q6 | A number-to-string cache for `o[i]` on non-arrays | M1 | V8-style small cache keyed by the number. **Filled 2026-10-27 (as built, M4-P2 STR2):** 1,024 direct-mapped entries per isolate next to the atom table (24 KiB), keyed by the number's bits (an int32 picks the slot by its value). `conv::number_string` (ToString) and `key::number_key` read it; a key hit is the atom (a cached plain string is interned in place first).
