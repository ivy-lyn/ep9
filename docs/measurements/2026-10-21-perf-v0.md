# Perf report v0, run 1: ep9 T0 at the P0 merge (2026-10-21)

The first cross-engine report of M0 week 4 (week-4 plan §11, decisions PERF-1..3). Run 1 measures
today's T0 at the P0 merge, before shapes, ICs, feedback and builtins. Run 2 (P4-PERFREP) measures
the P3 merge with the same tools and compares.

**Every number here is provisional.** The host file has no idle baseline yet (the shared machine was
never idle for 10 minutes on 2026-10-21; other agents were building and running test262), so the
load guard cannot pass. The 1-minute load was 3.58 before the run, 3.14-3.7 for the first 6 rounds, then up to 20.38 when other agents' test262 runs started, and 3.13 120 s after the run. No row passes or fails a gate.


- **richards: 0.239x QuickJS** (interval 0.228-0.245): ep9 takes 4.2x QuickJS's time. The M0 exit 4 canary (0.6x) needs a 2.5x speed-up. The whole interval is below 0.6; as a provisional run this is a reading, not a gate verdict. deltablue does not run yet (`Function.prototype.call`).
- **t0-call 0.374x, t0-prop 0.449x QuickJS.** The design probe (best of 3, load 10-12) had richards 0.25x, t0-call 0.40x, t0-prop 0.48x; run 1 agrees within a few percent. These three are the baselines to beat in run 2.
- ep9 is faster than QuickJS on the loop kernels: t0-loop 1.57x (void row), t0-branchy 1.46x.
- Against node `--jitless` (the M1/M2 gate comparator): richards 0.180x, t0-call 0.401x, t0-prop 0.389x; geomean of the 5 kernels 0.487x.
- **Where the time goes** (profile below): `props::find`, the linear property-table search, is 64% of richards and 58% of t0-call. Global variable loads are 47% of richards and 71% of t0-call; named property loads and stores are 39% of richards and 80% of t0-prop.
- Instructions do not equal time: on richards ep9 retires 6.8x QuickJS's instructions (45.4G vs 6.6G) but takes 4.2x its time.

## Slow paths (profile)

macOS `sample` at 1 ms on the same build, one run per workload, 09:23 (+08), 1-minute load 12-20.
The load changes the speed, but not much the shares within one process. The `ep9-isolate` thread
runs the script; the main and front-end threads only wait and are left out. "Handler" puts each
sample on the innermost bytecode handler of its stack (the handler plus the slow-path code it calls).

| Share of the isolate thread | richards (1041 samples) | t0-call (415) | t0-prop (411) |
|---|---|---|---|
| `LdaGlobal` (0x10) handler and slow path | **47.0%** | **71.1%** | 0 |
| `GetNamedProperty` (0x21) handler and slow path | **26.7%** | 0 | **70.5%** |
| `SetNamedProperty` (0x24) handler and slow path | 12.4% | 0 | 9.7% |
| everything else | 13.9% | 28.9% | 19.8% |

Top functions by self time:

| richards | % | t0-call | % | t0-prop | % |
|---|---|---|---|---|---|
| `ep9_vm::props::find` | 64.1 | `ep9_vm::props::find` | 58.3 | `ep9_vm::props::find` | 33.1 |
| `interp::slow::property::prop` | 5.3 | `CallUndefinedReceiver2` handler | 4.8 | `interp::slow::property::prop` | 14.6 |
| `memcmp` (+ its stub) | 5.1 | `Ldar` handler | 4.3 | `memcmp` (+ its stub) | 11.9 |
| `property::virtual_get` | 3.4 | `slow::property::load_global` | 3.6 | `property::virtual_get` | 8.3 |
| `GetNamedProperty` cold handler | 2.3 | `Star` handler | 3.4 | `property::get` | 7.1 |

What the profile says:

1. **One function is most of the time.** `props::find` (crates/ep9_vm/src/props.rs:72-79) searches
   an object's property table linearly and compares each key by content ("v0: linear search with
   content compare. Shapes replace it"). It is 64% of richards and 58% of t0-call.
2. **t0-call is slow because of global loads, not because of calls.** 71% of t0-call is `LdaGlobal`:
   each call of a global function first loads the function through `slow::property::load_global`
   (crates/ep9_vm/src/interp/slow/property.rs:19-46: the lexical record, then `property::has` and
   `property::get` on the global object), and both scan the global object's table, so a found
   global costs two scans. The call handlers themselves are about 12%.
3. **richards needs both fixes.** Global loads are 47%, named loads and stores 39%.
4. **Keys compare by content.** `memcmp` is 5% of richards and 12% of t0-prop. Plan §2 row 13
   (atom keys compare by bits) removes most of it.

So the week-4 work matches the cost, with one gap. The named get/set IC (P3-IC, sites 0x21 and
0x24) covers 39% of richards and 80% of t0-prop. But the global sites 0x10-0x12 are only a stretch
goal of P3-IC (plan §6, P3-IC task 6; §14 moves global-variable ICs to M1/M1a if the stretch
slips), and global loads are 47% of richards and 71% of t0-call. Even if every named access cost
nothing and the rest stayed the same, richards would reach only about 0.39x QuickJS
(0.239 / (1 - 0.391)), below the 0.6x canary.
