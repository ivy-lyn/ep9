## Where the round trip goes (evidence for the window)

As built (line numbers at e719ffa and 6146ec5, before the entry): a T0 call of a native-slotted function is sent to the cold path by T0's `call_fast` (any slot kind other than Interp, `crates/ep9_vm/src/interp/ops.rs:289-290`; decision M2-SPIKEB-REAL-T0). The cold path `slow::call` (`interp/slow/call.rs:39-48`) decodes the call instruction again with `call::decode_call` (`crates/ep9_vm/src/call.rs:572`), which builds the argument list as a heap `Vec<isize>` (`CallSite.args`, call.rs:565), and only then reaches the native branch `call_native` (slow/call.rs:246).

- **Profile** (samply, 4 kHz, `spike-b bench run A`, release, 9,544 samples): 78% of the time is under `CallAnyReceiver_cold` → `slow::call::call`. Self time: decoding (`decode_at`, `Instruction::operand`, `Opcode::from_u8`) 23.8%, malloc/free 18.0%, `slow::call` itself 19.8%; the T0 handlers of the loop 21.9%; the JIT code of `id` about 2%.
- **A/B experiment** (scratch copy only, never committed: a 25-line `cfg(feature = "spike-native")` branch at the top of `slow::call` that reads the `CallUndefinedReceiver1` operands in place and calls `native::enter_native`, with no decode and no `Vec`). 7 interleaved pairs on the gate host, load 5-7, tau 0.349551:

  | Build | RT per pair (dispatches) |
  |---|---|
  | as built (be48d9d tree) | 53.25, 46.64, 45.58, 44.63, 46.28, 47.43, 45.61 |
  | decode-free native entry | 17.55, 15.70, 15.81, 17.84, 16.89, 18.59, 17.85 |

  Cachegrind (linux arm64 Docker, n = 10^6): 654.8 → 226.6 Ir per iteration, ratio 100.9 → 31.6.

So about 29 of the 46 dispatches of run 1 are the cold path's second decode and its heap list, and a decode-free entry puts placement (a) at about 16-19, at the limit.

## What follows

- **Placement (b) is not started in P3** (task 6; decision row in the P3-SPIKEB-BENCH report). The provisional interval is above 18, but placement (b) built inside the P3 grant would be entered through the same `slow::call` cold path (T0's `call_fast` sends every non-Interp slot there), so it would carry the same cost and the measurement would not tell the placements apart. A T0 handler entry for (b) needs `ops.rs`, which no P3 role owns for this. `spikes/spike-b/src/jit_b/` keeps its stub.
- **For gate window 1:** the orchestrator decided that the measured placement (a) gets a decode-free native entry in `slow::call` (M2-P3-D21-ENTRY, `cfg(feature = "spike-native")`). The P3 integration fixer built it (next section). - The window runs `bash spikes/sp-dispatch/gate.sh` (SP_SPEED=gate) and then `bash spikes/spike-b/bench.sh` in a quiet window; bench.sh stops with "host busy" (exit 3) if the guard before fails after 30 min.

## With the decode-free native entry (M2-P3-D21-ENTRY; provisional, P3 integration fixer)

**What changed.** `slow::call` (`crates/ep9_vm/src/interp/slow/call.rs`, `native_entry`) now enters a native-slotted callee right after the interrupt poll for every unprefixed `CallAnyReceiver`, `CallProperty`, `CallProperty0`-`2`, `CallUndefinedReceiver` and `CallUndefinedReceiver0`-`2`: a range check on the opcode byte, the operands read at their fixed single-scale places, one argument reader per call shape, and `native::enter_native` (now `#[inline(always)]`). No `decode_call`, no `CallSite`, no `Vec`. A prefixed call, a spread call, a construct and any callee that is not native-slotted take the decode path as before. `cfg(feature = "spike-native")` only: the default ep9 release `__text` is byte-identical to 6146ec5 (`otool -t`, sha256 8243af26…), and DISASM gives 284 handlers on all 5 targets with the base handler stats. Commits 8e7952a, f6ab89c, 73639c6 on `m0m2/p3-fix-d21` (base 6146ec5); the measured spike-b binary was built at f6ab89c, and its `__text` is the same at 73639c6.

**How.** On the gate host `m5max-macos` (Apple M5 Max), one session, nothing built in between: `SP_SPEED=gate SP_CROSS=0 bash spikes/sp-dispatch/gate.sh` (08:20), then `SB_ALLOW_BUSY=1 SB_WAIT_MIN=0 SB_BIN=<binary> bash spikes/spike-b/bench.sh` for the binary with the entry (08:21) and for the as-built binary (6146ec5 sources, 08:25), both with tau from that bench.json.

**Why it is provisional.** It is not gate window 1. A fixer agent ran it on an unmerged branch while other agents could start work at any time (the window needs none running), with `SB_WAIT_MIN=0` and a tau run with `SP_CROSS=0`. The load guard happened to pass before and after both runs (loads 1.64-2.13, limit 3.005), so `bench.sh` added no "provisional" label and printed `VERDICT: fail (bench verdict: fail)` for both runs: the whole RT interval is above the limit 18, which is the fail rule of [protocol](2026-10-22-spike-b-protocol.md) §6 (with the entry [19.363, 21.750], as built [47.631, 48.027]).
