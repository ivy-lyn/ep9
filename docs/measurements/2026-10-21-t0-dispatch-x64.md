# T0 dispatch on x86-64 (2026-10-21): the match loop is not threaded, sibling calls win

- Trigger: the H15 reopen trigger "the x64 loop check fails on T0" ([ADR](../adr/H15-interpreter-dispatch.md), Reopens if). It fired on the real T0 interpreter of `ep9_vm` (157 opcodes, 282 handlers).
- Code: `crates/ep9_vm/src/interp/` (DSL and handlers), `tools/xtask/src/disasm.rs` (`cargo xtask disasm-check`), `tools/bench/workloads/` (kernels and the paired runner `t0-dispatch.mjs`).
- Result: on x86-64 the T0 match loop has 1 dispatch jump (a switch loop, not threaded code). Sibling calls are faster than match on every sampled CPU model (5 x86-64 models, 2 arm64 models), on every kernel. Decision: sibling calls are the release expansion on every target. Also kept: x86-64 handlers use the SysV ABI on every OS, which removes most Win64 handler frames (§7). The ADR has the decision; this file has the data.

```text
                     match loop (T0)                       sibling calls (T0)
x86-64 SysV, Win64   1 dispatch jump; 92-134 stack         1 indirect jump per handler; 0 non-tail
                     accesses away from calls              exits -> 1.21-1.47x faster (geomean, runs 1-2;
                                                           Win64 then +2-14% from the SysV handler ABI)
aarch64              1 dispatch jump (as in SP-Dispatch)   -> 1.26-1.53x faster
```

## 1. The x64 loop check fails on T0

`cargo xtask disasm-check --manifest-path crates/ep9_vm/Cargo.toml --match-loop --expect 282 --target <T>`, rustc 1.99.1, fat LTO. The rule needs dispatch jumps ≥ half of the 158 fast tail handlers (79) and no stack access away from a call, the entry block or an exit sequence.

| x86_64-pc-windows-msvc | 2 | 92 | 3520 | FAIL |
| x86_64-apple-darwin, before the xtask fix (§2) | 8 | 137 | 3467 | FAIL |
| x86_64-apple-darwin, after the xtask fix | 2 | 134 | 2989 | FAIL |
| aarch64-apple-darwin (report only) | 1 | 8 | 2888 | no rule |

- The same numbers come from the CI job of the diag runs ([run 1 job](https://github.com/Brooooooklyn/ep9/actions/runs/39500785277/job/118897445732), [run 2 job](https://github.com/Brooooooklyn/ep9/actions/runs/39502380399/job/118902826300), Linux host, cross builds).
- Of the 2 jumps on x86-64, 1 is the opcode dispatch. The other is a small `switch` inside one arm (8 entries).
- The sibling expansion passes the tail-exit check on all 5 targets: 280 of 280 tail handlers end in a tail jump, 0 non-tail exits, max 4 handler arguments.

## 2. Mach-O x86-64: jump tables in `__text` (xtask fix)

x86-64 Mach-O keeps jump tables in `__text`, after the code of their function (LC_DATA_IN_CODE). `llvm-objdump -d` decodes them as instructions. In `ep9loop__match__run` the 1056-byte table gave 6 false indirect jumps (`jmpq *-0x13(%rdx)`, `jmpq *0xbffffe2(%rbp)`) and false stack accesses. In `TestTypeOf` a 32-byte table reads as `jmpq *-0x1(%rax)`. Other bytes can read as `callq *` or `retq`, so a correct handler can fail the tail-exit check.

- Fix: `disassemble()` reads `llvm-objdump --macho --data-in-code` and drops the decoded "instructions" in those ranges. In an object the offsets are addresses. In a linked image they are file offsets, so the base is the vmaddr of the segment at file offset 0 (`__TEXT`); `--macho --private-headers` gives it.
- Checked on the staticlib member and on a linked `ep9` for x86_64-apple-darwin: both give 2 dispatch jumps. arm64 Mach-O has no data-in-code entries (its jump tables are not in `__text`).
- SP-Dispatch with the fix: `cargo xtask disasm-check --all-targets --expect 26 --match-loop` passes on 5 targets. Its x86_64-apple-darwin loop now has 16 dispatch jumps, as on Linux and Windows. The spike file lists 17: the 17th was table data.
- Tests: `macho_jump_table_is_data` (a negative control fails with 1 indirect call and 1 return; after the drop it passes) and `macho_data_in_code_base` (object and image headers).

## 3. Why LLVM does not thread the T0 match loop

Machine IR after early tail duplication (`-Cllvm-args=-print-after=early-tailduplication`), x86_64-unknown-linux-gnu:

```text
bb.1:   %op = load pc; MOV32r0; TEST8rr; JCC bb.2 (bad opcode)   <- range check of the jump table: always false
bb.724: jump-table load; JMP64r                                  <- the dispatch jump; 1 predecessor (bb.1)
```

- The `_ => bad_opcode(..)` arm is reachable, so the jump-table header keeps a range check. The table covers all 256 byte values, so the check is a constant false, but it stays: register allocation keeps the 0 in `%r15`, and every dispatch runs `testb %r15b, %r15b; jne`. The spike loop had `_ => unreachable_unchecked()`, so it had no check.
- The check splits the dispatch into 2 blocks. The jump block has 1 predecessor, so copying it gains nothing. The check block ends in a conditional branch; that block is too big for the 2-instruction limit.
- Without the check, the dispatch block has 159 successors, about 250 predecessors and 3 PHIs. Early tail duplication skips such a block (LLVM limits `-tail-dup-pred-size` and `-tail-dup-succ-size`, 16 each).

Probes (static, x86_64-unknown-linux-gnu; not kept):

| Probe | Dispatch jumps | Stack accesses away from calls |
|---|---|---|
| T0 as is | 2 | 111 |
| `_ => unreachable_unchecked()` (UB on a VM bug) | 2 | 214 |
| `-Cllvm-args=-tail-dup-pred-size=1000 -tail-dup-succ-size=1000` | 2 | 111 |
| both | 251 (threaded) | 320 (fail) |

So a threaded T0 match loop needs undefined behavior on a bad opcode and global LLVM flags for the whole binary, and it still spills on every arm. The interp agent also tried, with no change: cold blocks in out-of-line `#[cold]` functions, `-tail-dup-indirect-size=200`.

## 7. Win64 handler frames and the SysV handler ABI

`cargo xtask disasm-check -v` lists the handlers that build a frame on entry. Fast (not `_cold`) handlers with a frame, rustc 1.99.1:

| Target | Rust ABI handlers | `extern "sysv64-unwind"` handlers |
|---|---|---|
| x86_64-unknown-linux-gnu | 11 (the 9 call opcodes, `StaContextSlot`, `StaCurrentContextSlot`) + `BadOpcode` | the same |
| x86_64-pc-windows-msvc | 34 + `BadOpcode`: also `Add`, `AddSmi`, `Sub`, `SubSmi`, `Mul`, `MulSmi`, `Div`, `DivSmi`, `ModSmi`, `Inc`, `Dec`, `Mov`, `TestEqualStrict`, `LdaContextSlot`, `LdaImmutableContextSlot`, `GetKeyedProperty`, `JumpIfJSReceiver`, `ToObject`, `ConstructReturn`, the 3 for-in opcodes, `GetSuperConstructor` | 12 + `BadOpcode`: the Linux 11 and `GetKeyedProperty` |
| aarch64-apple-darwin | 10 + `BadOpcode` | unchanged (Rust ABI) |

- Cause: Win64 has only `rax`, `r10`, `r11` free when the 4 handler arguments use `rcx`, `rdx`, `r8`, `r9`; `rsi`, `rdi` and `xmm6-xmm15` are callee-saved. `Mov` decodes 2 register operands (2 temporaries each) and pushes `rsi`.
- Change: on x86-64, handlers use `extern "sysv64-unwind"` on every OS (`dsl::handler!`, `interp::Handler`). Win64 handlers then get the SysV register set. On Linux and macOS it is the same convention as before. `-unwind` keeps a panic (a VM bug) unwinding as before. Nightly `become` builds and passes the tail check with it (Win64, Linux, aarch64).
- The call handlers keep a frame on every target: the JS-to-JS call fast path writes the callee frame and fills parameters and registers (about 100 instructions); it needs more than the free registers. The 6 pushes are a small part of it. Not changed.
